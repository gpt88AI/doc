微信小游戏 AI 建游与上架：从一句话 3D 原型到真机审核的 4 步路线

AI游戏2026-11-2012 मिनट पढ़ें微信小游戏AI建游3D游戏DSH Game StudioDeepSeek HarnessCodexClaude Code

本文根据 Fini.Yang（@FiniYang）于 2026 年 11 月 20 日发布的 X 原帖及其关联的 X Article整理。X Article 正文可以通过公开接口读取，包含作者的实战案例、提示词和审核经验；下文把这些内容标为作者自述，不把“免版号”、账号额度、审核路径、冷启动或广告收益等平台规则写成无条件结论。工程能力和安装方式另以 ZSeven-W/dsh-game-studio 当前公开 README、package.json 和许可证为准。

很多 AI 小游戏 Demo 的问题，不是电脑浏览器里跑不起来，而是到了真实手机和微信小游戏环境就失效：画面黑屏、没有声音、按钮被右上角胶囊遮挡、资源超过主包限制，或者审核截图无法证明游戏真的在真机里运行。

Fini.Yang 这篇长文的价值，在于把“让 Agent 写一个小游戏”改成一条可以逐步验收的上线路线：先确认平台和账号规则，再安装跨宿主工具，接着用微信环境做试玩和静态检查，最后从同一份源码导出网页和微信小游戏包，并准备真实审核材料。

先看完整路线

文章将流程拆成四步：

  1. 核对平台规则和账号条件：确定游戏类型、主体、支付和广告方式，再判断适用的审核与备案路径。
  2. 安装 DSH Game Studio：把创建、构建、试玩、生成素材、版本回滚和微信导出等工具接入主力 Agent。
  3. 从一句话生成并预审：用 2D 或 3D 模板创建游戏，针对微信的胶囊安全区、WebGL、音频和包体积做检查。
  4. 导出、上传和准备审核材料：从单一源码生成微信小游戏包，上传体验版，在真实手机微信里截取审核图，再提交当前平台要求的资料。

这四步的顺序很重要。电脑浏览器里出现一个能玩的页面，只能证明第一层代码可以运行，不能证明它满足微信真机、包体积或审核要求。

第一步：先核对规则，不要把标题当成法规

X Article 的标题是“不用等版号！一个人靠 AI 搓出 3D 小游戏直接过审上线”。正文以作者发布的《一箱见底》为例，分享了个人主体、单机玩法、无现金内购、广告变现和备案并行等经验。

这些内容应当理解为作者在特定账号、特定游戏和特定时间的实操记录，而不是对所有开发者都成立的豁免条件。平台规则、主体要求、游戏类型、支付方式、广告能力、备案和内容资质都会影响审核路径。

开工前至少把下面几项写成自己的检查表：

  • 游戏是单机、联网还是带服务端功能；
  • 是否包含现金充值、道具内购、抽奖或兑换；
  • 是否计划接入广告，以及广告位属于哪一种形式；
  • 账号主体、游戏名称、AppID 和开发者工具环境是否一致；
  • 当前微信公众平台、小游戏开发文档和监管要求是否允许这条发布路径。

作者提到的“个人最多注册几个账号”“每年改名次数”“100 UV 后开通流量主”等数字，都可能随平台政策和账号状态变化。不要把文章中的数字直接复制成产品承诺；正式上线前应以登录后的当前后台和官方文档为准，并为审核材料留存截图和时间。

第二步：把游戏工坊装进 Agent

dsh-game-studio 当前仓库把游戏制作封装成一组 Agent 工具。README 标注的插件版本是 0.1.0-rc.6，提供 15 个工具，支持 DeepSeek Harness、Codex、Claude Code 和 Antigravity。

DeepSeek Harness 用户可以按仓库 README 安装：

dsh plugin --profile web add @zseven-w/dsh-game-studio@latest
dsh web

Codex、Claude Code 或 Antigravity 用户可以从仓库安装并运行对应的宿主配置脚本：

git clone https://github.com/ZSeven-W/dsh-game-studio.git
cd dsh-game-studio
npm install
npm run setup          # Codex
# npm run setup:claude # Claude Code
# npm run setup:agy    # Antigravity
# npm run setup:all    # 一次配置全部宿主

仓库还提供 npm run doctor，用于检查浏览器、图像服务和微信 CLI 等本机条件。安装完成后，不要只看 MCP 配置文件是否生成；应实际运行一次工具检查，确认 Agent 能创建游戏、启动试玩和读取结果。

这 15 个工具解决什么问题

仓库当前 README 将能力分成几组：

能力代表工具作用
创建与构建game_studio_create、game_studio_build从 2D 或 3D 模板创建游戏，修改后重新构建并保存版本
自动试玩game_studio_playtest用无头 Chrome 或 Edge 运行游戏，报告阶段、分数、帧率、脚本错误和截图
AI 素材game_studio_generate_asset、game_studio_apply_asset生成编号候选图，确认成本后选择并替换素材
版本管理game_studio_versions、game_studio_restore_version查看和恢复某一版游戏、规则与素材
导出与发布game_studio_export、game_studio_export_wechat、game_studio_upload_wechat导出单文件网页、微信小游戏目录和体验版上传
试玩分享game_studio_share在局域网或经用户批准的临时 Cloudflare Tunnel 分享试玩
游戏墙game_studio_list、game_studio_export_wall、game_studio_publish管理工作区游戏、导出离线游戏墙或发布到 GitHub Pages

AI 生图工具会在实际消费前显示确认卡，仓库也明确说明 API Key 不会写进项目、日志或工具结果。使用 OpenAI 图片服务或 Codex CLI 时，仍然需要检查当前账号、费用和图片许可。

第三步：一句话建游，但要用微信环境验收

仓库提供 2D top-down 和 3D voxel 两类模板。可以先从一个小而完整的玩法开始，例如“做一个 3D 游戏：小狐狸在月光岛上收集灯笼并躲开荆棘怪物”，等第一关能玩，再增加美术、关卡和音效。

初始提示词最好同时写清：

  • 竖屏还是横屏，以及单手操作方式；
  • 游戏目标、失败条件和一局的结束方式；
  • 所有界面文字使用哪种语言；
  • 是否允许外部网络请求；
  • 需要哪种真实图片或可替换的素材槽位；
  • 完成后必须运行哪种平台的试玩和截图检查。

微信真机的五类高频问题

X Article 结合作者的《一箱见底》案例，重点列出五类容易在电脑上漏掉、但会在微信真机暴露的问题：

  1. 运行时沙箱差异：浏览器里的 window、document、localStorage 或 requestAnimationFrame，在小游戏运行环境中不一定以相同方式存在。
  2. WebGL 上下文数量：主场景和缩略图、动效如果各自创建渲染器，手机可能因为上下文限制而黑屏。
  3. 右上角原生胶囊：微信胶囊会覆盖顶部区域，网页里看起来正常的按钮可能在真机上无法点击。
  4. 静音键与音频初始化：iPhone 静音状态、旧内核和 WebAudio 初始化方式会影响声音是否可听见。
  5. 主包体积：Three.js、未压缩图片和音频很容易把微信小游戏包推过仓库当前目标的 < 4.00 MB。

DSH Game Studio 的 game_studio_playtest 支持传入 platform: "wechat"，用于模拟微信右上角胶囊安全区和单 WebGL 条件。仓库的 game_studio_export_wechat 会从同一份 game.js 生成 wx-minigame/，并附带 WebGL2、Canvas2D、Pointer、WebAudio 适配层和提审草稿。

这类自动预审很有用，但它只能覆盖工具实现的检查项。真正的手机型号、微信版本、音频状态、网络权限和审核页面仍要做一次人工验收。

第四步：单源导出和体验版上传

这个工作流的关键取舍是维护一份游戏源码，再导出两个目标：离线网页和微信小游戏包。这样可以避免“网页修了一个 bug，微信分支还停在旧代码”的双份维护。

导出时，工具会处理一部分重复工作：

  • 写入小游戏兼容适配层；
  • 扫描多个 WebGL 上下文、英文残留和外链脚本等风险；
  • 把 SVG 槽位转成更适合包体积控制的图片；
  • 生成微信开发者工具可以打开的 wx-minigame/ 目录；
  • 输出 WECHAT_SUBMISSION_DRAFT.md，提前记录适龄、玩法和系统功能说明。

完成导出后，再把体验版上传到微信开发者工具。上传前要检查三件事：包体积是否低于当前限制、试玩画面是否与源码一致、上传备注是否写成面向玩家的中文简介，而不是随手留下英文开发日志。

不要把 AppID、私钥、开发者工具凭据或上传令牌写进提示词、博客或仓库。上传动作应在自己的本机环境中完成，并按工具的确认流程授权。

审核材料：证明“真机能玩”

X Article 建议准备 11 张真机截图，分为三组：

  • 场景图：微信原生启动页和两张核心关卡画面；
  • 玩法动作链：动作前、动作中、动作结果三张连续画面；
  • 系统功能：货币、道具、设置、商城和自定义等页面的对应截图与说明。

这套清单的核心不是“凑够 11 张图”，而是让审核人员能从真实手机画面看出：游戏名称和后台登记一致，核心玩法可以操作，系统功能有实际入口，右上角保留微信原生胶囊，截图不是电脑浏览器模拟出来的。

作者还总结了三个容易被打回的场景：用自绘图标冒充适龄标识、拿电脑截图替代手机微信截图，以及对抽奖、商城和支付关系写得不清楚。这些是作者案例中的审核经验，不能当成当前平台的完整审核规范。提交前应以微信公众平台当日显示的材料列表、尺寸和文字要求为准。

案例：作者如何验证《一箱见底》

Fini.Yang 在文章中使用自己制作的 3D 物理消除小游戏《一箱见底》作为完整案例。他自述该项目使用个人主体完成审核发布，并在后续版本中继续修复新手引导和操作路径；文章还给出了 3.60 MB 微信包、无强制插屏和预留激励视频入口等项目数据。

这些数字和上线结果属于作者在特定时间、特定账号和特定作品上的实测记录，不能直接推断其他游戏也能达到相同包体积、审核速度或广告表现。开发者应使用自己的手机、微信开发者工具、账号和游戏内容重跑一遍。

仓库 README 还提供了 在线游戏墙，可以在浏览器中试玩测试游戏；试玩墙是展示和验证入口，不等于你的微信小游戏已经通过审核或已开通流量主。

广告和上线后的边界

仓库的微信导出能力包含一个偏保守的广告辅助逻辑：默认不强制弹插屏，提供 watchRewardedAd 入口，并在尚未配置正式广告位时使用回退模式。这样可以让开发者先验证玩法，再决定什么时候接入真实广告。

广告是否可用、何时开通、需要哪些 UV 或认证、展示位置和素材要求，都属于平台账号和政策状态。不要把工具里的回退逻辑理解为广告收益保证，也不要在未确认资质前向用户承诺收入。

许可、隐私与依赖

ZSeven-W/dsh-game-studio 当前仓库标注 MIT License。仓库还列出了 Three.js、二维码库和 Playwright 等第三方依赖，并提供 THIRD_PARTY_NOTICES.md。

README 对隐私边界的说明包括：游戏在沙箱 iframe 中运行，导出文件默认不发起网络请求；只有用户选择的图片服务会接收相应提示词和参考图；分享链接是临时只读入口；发布到 GitHub Pages 需要用户本机已经登录的 gh，且发布动作需要确认。

使用时仍应逐项检查：

  • 生成图片、音乐、字体和第三方模型的许可；
  • 微信小游戏的隐私、网络、用户数据和广告要求；
  • 临时分享链接是否暴露了不应公开的素材；
  • 游戏源码、构建产物和日志中是否包含密钥、AppID 或个人信息。

总结

这篇 X Article 最值得借鉴的，不是“一个人也能一键上架”的宣传句，而是它把 AI 建游拆成了四个可验收阶段：规则核对、Agent 工具安装、微信环境预审、真机审核材料。

dsh-game-studio 当前仓库提供了较完整的工程骨架：2D/3D 模板、实时预览、无头试玩、版本恢复、AI 素材候选、单源导出和微信体验版上传。它能减少重复的适配和检查工作，但不会替开发者承担平台规则、内容合规、真实设备测试、素材许可和最终审核责任。

最小可行路线是：先做一款单关卡、无现金内购、玩法明确的小游戏；用 platform: "wechat" 跑通试玩；确认包体积、胶囊安全区、音频和新手引导；再导出体验版并用真实手机截取审核材料。等这条链路稳定后，再增加美术、关卡、广告和运营素材。
