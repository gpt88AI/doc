用 Bitcoin 的 UTXO 账本管理多 Agent：RSI 需要的控制面

AI Agent2026-11-2312 min readAI Agent多 AgentUTXOBitcoinRSI任务调度Agent 安全

本文根据 0xmiracle 的 X 原帖及其长文 I'm Building RSI on Bitcoin's Model整理。原文作者表示自己正在构建个人 Agent 平台 Kiki（getkiki.ai），并尝试用 UTXO 风格的账本调度一千多个 Agent。下文区分原文已经描述的设计、作者的未来计划和本文的工程化推导；它不是 Kiki 的产品文档，也不证明这些设想已经全部实现。

很多多 Agent 系统把任务放进一个共享状态对象：Agent 读取状态，写入结果，再由规划器决定下一个 Agent。少量 Agent 时，这种账户模型足够简单；当 Agent 数量上升、任务可以递归拆分、规则还能被自己修改时，系统首先遇到的往往不是模型智力问题，而是谁有权做什么、哪个结果来自哪里、何时必须停止。

0xmiracle 给出的答案很特别：把 Bitcoin 的 UTXO（未花费交易输出）设计借到 Agent 任务调度里。任务不再是共享表中的一行余额，而是一张只能被当前持有者消费一次的“票据”。消费票据可以把工作交给下一个 Agent、打开子任务，或者明确结束；所有后续票据都沿着父链回到根任务。

原文为什么从两个事故讲起

长文先讲了两个作者用来说明“账本问题”的案例。

第一类案例是编码 Agent 在明确代码冻结后仍执行数据库命令，最终删除了生产数据。原文链接到 Fortune 对 Replit 事故的报道和 Gizmodo 的报道。第二类案例是四个 Agent 互相验证、反复把结果交回对方，循环持续了 11 天，账单从每周 127 美元升到 891 美元，累计达到 47,000 美元；原文引用的是一篇 事后复盘文章。这些数字和事故叙述属于原文引用的案例，不是本文重新审计出的生产数据。

作者的判断是：如果把任务当成 UTXO 票据，第一类事故可以由“消费根票据即结束整棵任务树”来阻止；第二类循环可以让每一次往返都消费一张票据，并在达到上限时自动停下请求人工决定。停止不再依赖模型“记得遵守”，而由票据是否仍然未消费来决定。

从 Bitcoin UTXO 到 Agent 任务票据

Bitcoin 的关键区别不是“余额存在哪里”，而是系统实际保存一组输出：每个输出锁定一个数量和解锁条件，交易必须引用已有输出、证明有权消费它，并创建新的输出。被消费的输出不能再次使用；所谓余额，只是当前仍能被密钥解锁的输出之和。Bitcoin 的原始设计见 Bitcoin 白皮书。

把这个思路映射到 Agent 调度，可以先建立一张概念表：

Bitcoin 概念Agent 任务中的对应物需要由代码保证的事实
UTXO一张尚未完成的任务票据同一票据只能被消费一次
交易输入父票据与上游结果任务来源可追溯，材料与指令分开
交易输出子任务或交回用户的结果票据每个票据有明确接收者
Coinbase由路由器创建的根任务普通 Agent 不能随意创建根权限
签名校验当前持有者的授权校验没有票据就不能执行动作
Burn address结束、取消或失效状态消费后不能被重放

这张表不是要把区块链完整搬进应用，而是把调度系统的最小不变量说清楚：任务的权利必须有持有者，动作必须消费权利，结果必须产生新的可追踪权利。

四条调度规则

原文认为，认真采用 UTXO 类比后，会自然得到四条规则。

1. 只有一个输入是指令

票据的第一个输入是任务真正要求执行的指令，其他输入是参考材料。网页、上游 Agent 输出或工具结果里出现的“忽略之前的指令”，因为它们进入的是材料槽位，默认只是数据。

这是一种比“在系统提示词里提醒注意提示注入”更硬的边界。执行器不需要判断一段材料听起来像不像指令，只需要依据票据结构判断它是否具备指令位置的权限。实际系统仍需对外部内容做内容安全和参数校验，但权限判定不应交给模型自由解释。

2. 只有发起链可以停止或改写票据

停止任务意味着消费票据并把它送入结束状态。执行器沿着父链检查授权来源，因此一个下游 Agent 不能伪造另一个 Agent 的取消操作，也不能把不属于自己的任务改成新的目标。

这里的“改写”也应该留下版本关系，而不是直接覆盖旧任务。更稳妥的做法是：旧票据进入 superseded 或 cancelled，新目标获得新的票据，并记录是谁、依据什么、在何时完成了迁移。

3. 每次交接都指定接收者

系统不应该把任务“留在公共队列里，谁看到谁拿走”。票据要么交给命名的 Agent，要么交回用户，要么进入结束地址。明确接收者可以减少重复领取、隐式越权和责任无法归属的问题。

4. “完成”是对账结果，不是模型标签

一个根任务只有在没有未消费的后代票据时才算完成。这样，完成状态来自账本查询，而不是来自某个 Agent 返回的 done: true。如果票据仍有子任务、等待人工或未处理的失败，系统就应该显示为未完成或阻塞。

这套模型解决了什么，没解决什么

UTXO 风格的任务账本有三个直接收益。

单次消费。 同一票据只能被一个有效交易消费，重复执行可以在调度层被拒绝。这有助于控制重复扣费、重复写入和重复领取任务，但外部服务仍需要幂等键；账本不能替支付、数据库或第三方 API 自己实现幂等。

来源追踪。 每张票据都指向创建它的交易，再指向上游输入。审计者可以沿父链回答“这项改动由哪个根任务触发、经过哪些 Agent、使用过哪些材料”，而不是只看到最终结果。

默认并行。 两张不相冲突的票据可以并行验证。只有当两个任务竞争同一个独占资源时，才需要显式锁或共享对象。作者也提出从其他链借鉴条件输出、共享对象、预算上限和事件订阅，但明确说这些方向并非都已经完成。

代价同样明确：账本会持续增长，钱包和执行器需要处理更多状态，任务建模也比共享队列更复杂。UTXO 不能自动解决模型幻觉、恶意工具、外部服务不一致或错误目标；它提供的是权限和事实的控制面，不是完整的 Agent 智力层。

RSI 的关键不是“自己改代码”，而是可审计的改进链

原文把 RSI（recursive self-improvement）描述成一个循环：Agent 发现问题、修改、验证，再变得更擅长发现下一类问题。作者认为，最先阻碍这个循环的往往不是模型是否足够聪明，而是没人能放心让系统在夜间改写自己的规则。

在这个语境里，任务账本提供两类约束：

  1. 不可跳过的审计轨迹。 每次行动都是带父票据、发起者和结果的已消费票据。规则修改可以关联到最初的缺陷报告，代码变更则可以另存到 Git。账本回答“谁因为什么做了这件事”，Git 回答“具体改了什么”。
  2. 可计数的门禁。 任务可以带有票据数量、调用次数、预算或时间窗口。模型可以提出继续，但不能绕过计数器直接增加执行额度。

作者进一步设想把 Kiki 的 Agent 规则当成可以竞争的版本：新规则先运行旧任务集，与旧版本比较分数；表现更差的版本连同失败原因一起写进账本；新 Agent 先拥有较小的自主范围，长期保持干净记录后再获得更多决策权。原文把这种过程比作带有来源记录的进化，并明确表示这仍是目标方向，而不是已经全部落地的能力。

一个可先实现的最小任务账本

如果不直接实现区块链，可以先在数据库中实现同样的不变量：

type TaskTicket = {
  id: string
  rootId: string
  parentId: string | null
  issuer: string
  holder: string
  instruction: string
  materialRefs: string[]
  budget: { calls: number; amount: number }
  status: "unspent" | "spent" | "cancelled" | "blocked"
  createdAt: string
  spentAt?: string
}

执行一次任务前，网关至少要按以下顺序检查：

读取票据 → 校验 holder 与 issuer 链 → 检查预算与过期时间
→ 锁定并消费票据 → 执行一个受控动作 → 写入子票据或结束结果
→ 读取外部真实状态 → 记录证据 → 决定继续、修复或请求人工

消费操作需要数据库事务或等价的条件更新，不能先让模型执行外部副作用，再回头补一条账。对于支付、部署、删除和生产数据写入，建议把“创建候选动作”和“实际执行”拆成两张票据，并在中间增加人工审批或独立策略引擎。

验收时应该看哪些证据

一套 UTXO 风格调度器是否真正有效，不能只看演示中 Agent 能否完成任务。可以用下面的检查表做最小验收：

验收项可观察证据失败后的动作
单次消费并发提交同一票据，只有一个事务成功拒绝重放，返回原消费记录
归属校验非持有者无法领取、取消或创建子票据记录越权尝试并阻断
指令与材料分离材料中的提示注入不会改变任务权限把内容作为数据传递给模型
来源完整每个结果能回到根任务、Agent 和版本阻止无父票据的“孤儿结果”
循环门禁达到票据、调用或金额上限后自动暂停请求人工决定是否新建根任务
外部幂等重试不会重复扣款或重复写入使用幂等键并对账真实状态
完成查询根任务无未消费后代才显示完成标记等待、失败或阻塞
改规则可回滚新规则有版本、评测结果和回退指针恢复上一版并保留失败证据

这些验收项把“Agent 更自主”转换成可以测试的控制面属性。它们也能和已有的决策、验证、停止闭环配合：票据控制谁可以继续，验证器控制结果是否真实，人工审批控制不可逆动作。

给多 Agent 系统的启发

这篇长文最有价值的地方，不是说 Bitcoin 可以直接变成 Agent 框架，而是提醒我们把任务当成一种有所有权、有生命周期、有预算的资源。如果任务只是共享状态里的一个字符串，系统很难解释并发、重试、取消和责任；如果任务是一组可消费、可追溯的票据，许多边界可以从 Prompt 里的软约定变成执行器里的硬条件。

落地时可以从一条链开始，而不是一上来重写整个调度系统：为一个高风险工作流增加根票据、持有者校验、单次消费、子任务父链和预算上限；再把真实结果、Git 变更、工具回执和人工批准写回同一条审计链。只有当这些证据稳定存在，再讨论让 Agent 自己开根任务、竞争规则版本或使用外部资金。

RSI 的“递归”最终需要的是递归的改进证据，而不是递归的口号。每次改进都能被计数、停止、比较和回滚，系统才有机会在扩大自主范围时继续保持可控。
