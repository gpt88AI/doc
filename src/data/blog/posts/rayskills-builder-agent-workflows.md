## 它解决的不是“提示词够不够长”

很多 Agent Skill 只描述应该如何回答。rayskills 选择把常见工作拆成明确阶段：读资料、形成稿件、做封面、准备平台草稿，并给阶段之间定义交接材料和检查点。

它面向使用 Claude Code、Codex 等 Agent 的 Builder。入口 `/ray` 根据当前上下文判断下一步；当目标和交接条件都明确时，再把任务交给多个 Skill 连续处理。这个“先选择、再编排”的做法，减少了用户必须记住所有 Skill 名称的负担，也避免每个请求都机械跑完全套流程。

## 八个入口围绕两条主线

按 README 展示的目录，这个版本由 `/ray` 路由器和七个成员组成：

| Skill | 主要职责 | 常见输入 |
| --- | --- | --- |
| `/ray` | 判断当前处境，选择下一步；条件成熟时组织完整流程 | 尚未拆解的目标或一组已明确的交付要求 |
| `/ray-obsidian` | 检查或增量建立本地内容知识库 | 空目录或已有 Obsidian 库 |
| `/ray-writer` | 把想法、资料或草稿发展成长文，也支持译介和口播相关工作 | idea、剪藏、来源资料、已有稿件 |
| `/ray-kb` | 从灵感或核验过的内容生成口播稿 | 现场观察或定稿长文 |
| `/ray-cover` | 按渠道要求为文章或视频准备封面 | 已定稿的文章或视频 |
| `/ray-explainer` | 将文章或剪藏转成知识讲解视频制作流程 | 文章、剪藏、已经整理的内容脚本 |
| `/ray-wechat` | 排版、预览并准备微信公众号草稿 | 定稿和公众号封面 |
| `/ray-x-article` | 检查并准备 X Articles 草稿 | 长文和横版封面 |

可以把它们看成两条相连的主线：知识库和写作负责生产内容，封面与平台 Skill 负责形成可检查的发布草稿。口播或解说视频则是从内容母稿分出的另一种交付方式。

## 从一个主题到平台草稿

例如，要把一个产品观察变成公众号长文和 X Article 草稿，可以先让 `/ray` 判断是否需要补充资料，再进入写作和封面环节。定稿之后才交给平台 Skill 做格式预览、草稿更新和回读检查。

关键点在于“草稿”是这条管线的停靠状态，而不是“发布”的委婉说法。README 描述的流程会在公开发布前停住；写入草稿也要验证预览、正文、署名和保存状态。需要授权的译介内容还会先经过来源许可与署名检查。这样设计能把内容生成和对外发布分开，让作者保留最终决定权。

知识库也是类似的风险边界。`ray-obsidian` 强调先检查、再适配已有目录，尽量避免覆盖或移动用户已有笔记。对于一套可能读取本地资料并执行脚本的 Agent 工作流，这类“不破坏已有数据”的规则比增加更多自动化步骤更重要。

## Skill 的质量主张需要怎样读

仓库 README 报告了结构校验、场景用例以及带 Skill 与不带 Skill 的对照结果。这些数字是项目维护者提供的自测结果，不等于独立评测，也不能自动代表其他模型、客户端、任务集或当前版本的表现。

更有参考价值的是它把评测边界讲成了具体失败方式：是否虚构作者经历，是否遗漏出处，是否覆盖本地文件，草稿是否真的保存成功。这些问题可以转成自己的验收用例。团队试用时，应从最常用的两三个流程开始，记录输入、预期交付、禁止动作和失败恢复方式，再用自己的资料和客户端复跑；不要只看演示成功的样例。

## 安装与使用起点

README 给出的安装方式是通过 Skills CLI 添加整个仓库：

```bash
npx -y skills add imraywang/rayskills -g --all
```

也可以按仓库说明，在支持上传 Skill ZIP 的 WorkBuddy 技能页面导入构建产物。不同 Agent 对全局目录、调用命令、脚本权限和工具连接器的支持并不相同，安装后先确认宿主能否识别 Skill，再用低风险任务验证调用和文件权限。

第一次使用可以从 `/ray` 开始，描述你手头的资料、目标渠道以及希望它停在哪个状态。例如“把这份已核验资料整理成公众号草稿，先预览和保存，不要发布”。如果已经知道要执行哪个局部任务，也可以直接调用对应成员。先试单步，再试跨阶段交接，比较容易定位配置或工具权限问题。

## 适合谁，什么情况下要谨慎

rayskills 适合需要重复进行内容整理、长文生产和平台草稿准备的个人 Builder 或小团队。它的特色不是单个 Skill 的万能程度，而是把实际工作里的顺序、输入和停止条件组织起来。

但 Skill 仍然运行在宿主 Agent 的权限之内。它不能替代备份、权限控制、人工事实核对或平台自身的发布审核。涉及客户资料、未公开信息、真实账号写入和外部发布时，应先确认宿主能访问什么、数据会发往哪里，以及工作流在哪一步停下。

如果你的需求只是一次性问答，或只需要一个高度专门的单点工具，整套工具箱可能带来额外维护成本。可以先挑一个重复且边界清楚的环节试用，等它能稳定复现并通过本地验收，再考虑扩大流程范围。
