花叔这次发布的重点，不是再增加一个只会生成页面的提示词模板，而是把“让 Agent 做设计”整理成一套可以交付、可以修改、可以检查的工作流。项目 README 把它概括为：在 Agent 里输入一句话，拿回一份能继续编辑和交付的设计。

## 3.4 增加了什么

当前仓库 README 把 3.4 的变化归纳成两项：App 原型工作流重新设计，以及新增 App Store 宣传图模块。

### App 原型先理解现实，再画界面

项目称自己走查了两届 App Store Awards 的 90 个入围作品，并从中整理出八条界面范式。这里的思路是先判断一个 App 在现实世界里“管理的事”是什么，再决定屏幕如何组织，而不是先套一个通用的卡片布局。

这条原则可以这样理解：

- 观鸟记录可以从照片、贴纸和声音这些真实对象出发；
- 菜谱应用可以把一道菜组织成一页有旁注的“方子”；
- 植物健康应用可以把数据表现成生命体征，而不是一组无语义的指标卡。

README 的案例描述了这些具体方向，但它们是项目展示和作者自述，不代表每个主题都能自动得到同样结果。实际交付仍然需要提供真实内容、检查事实，并由人确认信息层级是否清楚。

### App Store 宣传图成为独立交付物

3.4 新增了 App Store 宣传图模块。README 给出的目标画布是 **1320×2868**，支持多张上架图、连续画面、破框构图和搜索结果缩略预览。

这和普通 App 截图有三个不同点：

1. 每一张图要在商店列表中单独成立，不能只把一张长画面机械切开。
2. 一组图需要有连续的叙事和视觉节奏，而不是每页换一个随机模板。
3. 设计时要同时看大图、连幅效果和缩小后的搜索结果预览。

仓库还提供了尺寸检查和 App Store 相关脚本。它们可以减少出界、比例错误和缩略图不可读等机械问题，但不能替代对产品卖点、截图真实性和商店规范的人工检查。

## 它可以交付哪些东西

README 当前列出的交付范围包括：

| 任务 | 典型交付物 | 项目说明的时间范围 |
| --- | --- | --- |
| App 或 Web 交互原型 | 单文件 HTML、可点击的设备外框、多屏状态切换 | 10–15 分钟 |
| 演讲幻灯片 | HTML deck 与可编辑 PPTX | 15–25 分钟 |
| 时间轴动画 | MP4、GIF、插帧版本和配乐 | 8–12 分钟 |
| 设计变体 | 多个方向并排对比和实时调参 | 约 10 分钟 |
| 信息图 | 印刷级排版，可导出 PDF、PNG 或 SVG | 约 10 分钟 |
| 小红书图文 | 3:4 竖图、长卷和封面 | 10–15 分钟 |
| App Store 宣传图 | 1320×2868 上架图和缩略预览 | 10–15 分钟 |
| 设计方向顾问 | 多个逻辑方向、候选方案和选择建议 | 约 10 分钟 |
| 专家评审 | 六个维度的雷达图、Keep/Fix/Quick Wins | 约 3 分钟 |

这些时间是 README 的项目说明，不是本文测量出来的承诺。机器性能、模型、素材准备、浏览器渲染和修改轮次都会改变实际耗时。尤其是原型、PPTX 和 App Store 宣传图，是否能交付取决于图片、字体、品牌资产和事实资料是否已经准备好。

## “该是图的地方放真图”

3.4 的另一个明确变化，是把真实图片素材放到更重要的位置。README 说明：如果设计里应该出现产品界面、照片、商品或场景，就不要用 emoji、空白色块或抽象占位块顶上去。

项目给出的素材路线是：优先使用当前环境可用的生图能力；没有合适的生图能力时，再借助本机工具、用户提供的 API 或开放许可图片。环境支持时，Skill 也会根据任务决定是否需要真实图片、品牌资产或参考截图。

这条规则对产品设计尤其重要。一个“看起来像 App”的空壳原型，不能证明 Agent 真的理解了产品；一张没有真实内容的商店宣传图，也不能说明用户在商店里会看到什么。素材来源、图片许可和产品事实仍然需要单独确认。

## 设计方向不是一次生成一个答案

`SKILL.md` 把工作流定义成“先探索方向，再做完整交付”。当前版本的方向流程会先写出多个互补候选，再选择几个方向完成真实初稿；方向之间的差异应该来自设计逻辑、媒介和参考机制，而不是只换颜色。

项目把参考作品的使用总结为“借一层，不借一身”：先看原图和数据，再借用结构、信息顺序或某个机制，最后让配色、字体和内容表达从当前题材重新长出来。这个原则也解释了为什么仓库强调要截取参考图、量尺寸，并把做完的版本和参考并排比较。

如果只是把一个通用模板换成紫色、蓝色或橙色，不能算完成了设计探索。对于 Agent 工作流，保留方向卡、参考依据和用户选择，也比让模型直接输出一份不可解释的成稿更容易返工。

## 代码化的交付方式

`huashu-design` 的核心媒介是 HTML。它把网页、原型、动画、信息图和演示文稿视为可运行的代码组合，而不是一张只能导出的静态图片。

这种方式带来几个实际好处：

- 原型可以在浏览器里点击和检查；
- 文案、颜色、数字和版式参数可以继续编辑；
- HTML deck 可以转成保留文本框的 PPTX；
- 动画和信息图可以在改完数据后重新渲染；
- Playwright、截图和尺寸脚本可以覆盖一部分机械检查。

取舍也很清楚：使用者需要能运行 Node.js、浏览器和项目所需的导出工具；视觉质量依赖模型、素材和人工反馈；自动检查通过不等于作品已经适合发布。代码化交付保留了可修改性，但没有消除设计判断。

## 安装和第一次使用

README 给出的通用安装命令是：

```bash
npx skills add alchaincyf/huashu-design
```

项目支持 Claude Code、Codex、Cursor、OpenClaw 和 Hermes 等 Agent。安装后，仓库建议检查 Skill 目录中是否同时存在 `references/`、`assets/`、`scripts/` 和 `demos/`，因为完整工作流不只依赖一个 `SKILL.md` 文件。

如果本机的 Skills CLI 版本太旧，也可以直接克隆仓库：

```bash
git clone https://github.com/alchaincyf/huashu-design.git ~/.claude/skills/huashu-design
```

这是一个安装路径示例。不同 Agent 的 Skill 目录不同，实际使用时应按对应客户端的文档放置，避免把仓库误当成生产 Web 应用直接部署。

## 许可与素材边界

GitHub 仓库当前标注 **MIT License**。这意味着仓库中受 MIT 覆盖的代码和文档可以按许可使用、修改和再发布，但不能把仓库里的每一份演示资源都自动理解成同一许可。

README 和项目文件仍然要求使用者留意字体、音频、角色形象、第三方组件、模型和下载素材的各自许可。把 Skill 安装到本机，不能自动取得这些第三方资源的商业再分发权。准备把生成的图片、字体或音频放进商业产品时，应逐项保留来源和许可记录。

## 适合什么，不适合什么

比较适合：

- 需要快速比较多个视觉方向的产品概念；
- 需要可点击的 App 或 Web 原型；
- 需要可编辑的 HTML deck、PPTX、信息图或宣传图；
- 希望把截图、尺寸、布局和部分可访问性问题纳入检查；
- 愿意在浏览器中查看结果并进行至少一轮人工修改。

需要谨慎评估：

- 生产级 Web App、后端系统或需要数据库的产品开发；
- 需要真实人物、实拍场景或复杂自然运动的内容；
- 完全没有浏览器、Node.js 或导出依赖的环境；
- 期待一次提示词就得到最终商店素材，并跳过事实、品牌和许可审查；
- 把 README 的样片、耗时或模型体验当成跨设备、跨模型的独立基准。

更稳妥的使用方式是：先提供产品真实界面和品牌资产，选定方向后再做完整页面，最后用真实尺寸截图、浏览器交互和目标平台预览检查交付物。

## 总结

`huashu-design 3.4` 值得关注的地方，是它把 Agent 的设计工作从“生成一张看起来不错的图”推进到一条可检查的交付链：先理解题材和真实素材，提出多个设计方向，再用 HTML 生成可点击、可编辑、可重新渲染的结果，并为 App Store 宣传图、PPTX、动画和信息图提供相应的交付模块。

它并没有把设计判断、事实核验、品牌资产管理或许可审查自动化。把它当成一个可复用的设计工作台更准确：Agent 负责研究、组织和执行，人负责选择方向、检查内容和批准最终交付。
