## 核心不是同时打开三个聊天窗口

作者分享的重点不是让 Claude、GPT 和 Gemini 对每个问题都回答一遍，而是把它们放进一条有主次的工作流：一个模型理解目标、规划和验收，其他模型在适合的环节提供独立方案、模块实现、审查或浏览器操作。

这套安排背后的实际问题是协调成本。模型越多，交接、补充上下文、对齐接口和复核结果的工作也越多。只有当任务足够大、子任务边界足够清楚时，并行才可能节省时间；几十行的小改动通常直接完成更划算。

## 作者对三个模型的个人画像

原文先描述作者在写作、编码、视觉和电脑操作中的主观体验，再据此分工。为了避免把体验误读成排名，可以将它概括为任务偏好，而不是模型的固定能力结论：

- **Claude**：作者主要用作任务主协调者，负责理解需求、拆解计划、组织其他模型并最终验收；前端视觉实现也由它主做。
- **Gemini**：作者把它作为方案顾问，尤其在大方案和界面文案、交互设计上，要求它独立提出意见，再由主协调者结合实际代码和产品需求判断是否采纳。
- **GPT / Codex**：在接口已经确定、与页面分离的后端、算法或数据模块中承担实现任务；GPT 也被作者用于代码审查和浏览器操作。

这些角色不是互斥边界。任务切分、模型版本、工具能力和项目上下文都会影响结果。应把它们看成作者在特定时间形成的工作假设，再用自己的任务样本验证。

## 一条完整的协作链路

### 1. 由主协调者先澄清目标

较大的任务先由主模型接收用户原话和必要背景，补齐目标、约束、成功标准和可能遗漏的工作。它负责把需求变成可以验收的任务，而不是马上把一句模糊指令分给多个模型。

在交给其他执行者前，至少要明确：要改什么、涉及哪些文件或接口、不能做什么、如何验证，以及遇到哪些情况要回来询问。任务越独立，交接越有效。

### 2. 大方案让两边独立出稿

对重要方案，作者会让主模型自己形成一份方案，同时把原始需求和必要上下文交给 Gemini 独立分析。关键在于不把自己的草稿或倾向先给第二方，否则所谓“独立意见”容易被锚定。

随后由主协调者对比两份结果：一致的部分可以作为较强候选；分歧要回到代码、数据和官方资料核实；无法验证且影响方向选择的分歧，应明确列出，而不是伪装成已经解决。第二模型的意见是交叉检查，不是自动正确的裁判。

小问题则不必套用这一流程。若交接和汇总成本高于任务本身，直接完成更简单。

### 3. 视觉与交互采用顾问模式

作者的前端做法是由主模型先实现视觉与界面，再让 Gemini 针对文案和交互提出改进建议。咨询时提供页面面向谁、用户要完成什么、当前方案和相关上下文；回来后由主模型对照真实产品行为核实和采纳。

这比让多个模型同时改同一套界面更容易控制。顾问提出的是候选意见，最终界面仍需要结合已有组件、无障碍需求、移动布局和实际操作路径验证。

### 4. 只把接口稳定的独立模块交给编码执行者

作者把较大的后端、算法、数据处理或性能模块交给 Codex 的前提，是接口已经明确且工作与页面分离。主模型负责定义接口与验收标准；执行者完成自己的模块后，主模型读取 diff 并自行跑检查。

如果要写的部分只有几十行、接口仍在变化，或者实现要和页面反复来回确认，拆分反而会制造额外协调。这个判断比“尽可能并行”更重要：并行任务应当在边界确定后再分派。

### 5. 让独立审查成为交付关卡

完成实现后，作者让另一模型做最终代码审查，并把问题分成两类：会导致真实故障或阻塞交付的问题，以及可考虑改进但不应阻止交付的建议。这样可以减少低价值的无限挑错，也让“发现问题”和“建议风格优化”不会混为一谈。

审查结论仍要由人或负责交付的主模型对照代码确认。对重复出现的问题，值得补测试、静态检查或结构约束；对无法机械检查的部分，才保留简明的文字规则。审查模型不应替代运行项目检查、测试或确认线上结果。

### 6. 浏览器操作按实际任务能力分工

原文中，作者把浏览器操控交给 GPT，因为这是他在当时观察到更稳定的选择。这只是个人环境里的实践结论。实际选择时，应该先用目标网站和真实流程做小样本验证，尤其是登录状态、多步骤表单、提交确认和结果校验。

任何会发消息、提交表单、修改设置或产生外部副作用的浏览器任务，都应设置清晰的操作边界和确认点。模型完成点击不等于业务结果已经成功，仍需读取页面状态或服务端结果核实。

## 把一次纠错变成可复用的防线

作者也分享了一个持续改进规则：当模型被纠正或审查退回时，尽量在同一变更里阻止同类错误再次出现。能通过类型、测试或脚本判断的，就加入自动检查；能通过接口或目录结构避免错误用法的，就调整结构；只有自动化办法不合适时才写文字约定，并说明原因。

这条思路有助于把经验沉淀下来，但检查规则也需要可维护。适合自动化的检查应有明确报错和修复方向；新增规则不应让旧问题被误认为已解决。对代码仓库而言，最小可行做法是先为高频、易复现的错误加一条测试或 lint 规则，而不是一次性写一份庞大、没人维护的指令文件。

## 可复用的分派模板

把任务发给另一个模型前，可以用下面的结构写清上下文：

```text
目标：要交付什么结果
背景：与判断直接相关的用户原话、代码和约束
边界：负责范围、明确不负责的部分、权限限制
接口：输入、输出、依赖或文件范围
验收：需要通过的检查、可观察的完成条件
升级条件：哪些不确定性或副作用必须先回来确认
```

返回时要求说明改了什么、执行了哪些检查、哪些未验证、有哪些已知限制。主协调者应检查实际 diff 和运行结果，不能只把“已完成”当作验收证据。

## 一套简单的分流规则

| 任务情况 | 建议做法 |
| --- | --- |
| 小改动、边界清楚、低风险 | 一个模型直接完成并验证 |
| 大方案、决策影响较大 | 两个模型独立分析，主协调者核对证据并处理分歧 |
| 接口稳定、与其他部分解耦的模块 | 分派执行，再由主协调者检查 diff 与验收结果 |
| 文案或交互有多种合理选项 | 一个模型先出稿，另一个给顾问意见，结合产品行为筛选 |
| 代码即将交付 | 独立审查加项目自动检查，问题按阻断程度分类 |
| 涉及外部副作用的浏览器任务 | 先核实目标环境和边界，操作后读取结果确认 |

## 结语：管理任务，也管理注意力

作者用刘邦与张良、萧何、韩信的典故来比喻模型协作：每个执行者各有长短，关键是清楚目标、分配合适任务，并验证最后结果。对今天的多模型工作流来说，最可迁移的部分不是固定的“谁最强”，而是几个方法：让复杂任务有主协调者，让独立意见真正独立，让执行任务具备清楚接口，让审查与验证有明确标准，并把重复错误转成可检查的约束。

模型数量不等于协作效率。先把单个任务的交付标准说清，再判断是否需要并行；如果需要多人式协作，就把上下文、权限和验收随任务一起交接。这样得到的才是可复用流程，而不是多开几个窗口。
