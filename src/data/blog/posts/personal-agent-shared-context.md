> 本文根据逸尘于 2026 年 10 月 17 日发布的[X 帖](https://x.com/gengdaj/status/2111344530490552560)整理。作者把个人 Agent 的重点放在“共享世界上下文”：让助手在获得授权后，能从自己的资料中检索相关信息。本文是对这一思路的归纳和编辑补充，不代表相关工具已经具备完整、安全或永久兼容的保证。

一个个人 Agent 是否“懂你”，不只取决于模型能力，还取决于它能否在合适的时刻找到可信的个人信息。逸尘的做法不是先寻找一个万能应用，而是逐步把不同来源的记录接入可检索的个人资料库，再让 Claude Code 等 Agent 按任务读取。

## 从分散记录到个人上下文

作者列出的资料入口包括即时通讯、邮件和协作工具、电脑操作记录、线下会议录音转写、社交平台收藏，以及 Codex 和 Claude Code 的对话历史。它们分别记录了关系沟通、工作决策、临时灵感和个人偏好。若这些资料长期分散在各个平台，Agent 每次都只能依赖当前对话里有限的上下文。

因此可以把流程理解为四步：

1. **采集**：从本人有权限访问的来源导出记录，不默认绕过平台访问限制。
2. **整理**：转换成 Markdown 等可读格式，保留时间、来源和必要的上下文。
3. **检索**：根据当前任务取回少量相关片段，而不是每次把所有历史都交给模型。
4. **回写**：只有经确认的稳定结论才沉淀为长期记忆，并保留来源和修订记录。

把“我眼即 Agent 眼”落到工程上，关键不是让模型持续读取所有数据，而是建立一个由用户控制的上下文层：哪些来源可接入、保存多久、什么任务可以读取、哪些内容必须留在本机，都应有明确规则。

## 把资料来源分成不同层次

### 对话与沟通记录

微信、企业微信、Gmail、Slack、Lark 等记录了沟通内容，但不同平台的导出方式、权限和本地存储结构并不相同。作者分享的仓库包括[微信本地数字资产库](https://github.com/mcncarl/yichen-skills/tree/main/yichen-wechat-local-vault)和[企微本地资料库](https://github.com/mcncarl/yichen-skills/tree/main/yichen-wecom-local-vault)。归档材料最初把微信和企微链接混在一起，作者随后补充了正确的微信仓库链接；使用前应以仓库当前 README 和平台规则为准。

私聊和群聊信息往往包含第三方的个人资料、商业信息或敏感内容。只有本人有权限处理的记录才应进入资料库；即使本地保存，也应限制目录权限、加密备份，并避免把整库同步到公开仓库或不受控的云服务。

### 会议与语音记录

线下会议、录音笔和语音 App 可以产生重要的决策上下文。语音转成 Markdown 后，建议附上日期、参与者范围、录音来源和转写状态，并区分原话、模型摘要与后续补充。自动转写会有错字和说话人归属错误，重要决策应回听或由参与者确认。

### 收藏与稍后阅读

X 书签、小红书收藏和抖音收藏反映的是兴趣线索，不等于稳定偏好或事实知识。作者提到的[收藏导出工具](https://github.com/mcncarl/yichen-skills/tree/main/yichen-bookmarks-export)强调读取明确授权范围，并把结果作为本地 URL 文件。链接可以进入检索索引；是否保存原文、图片或视频，应另外考虑授权、隐私和版权。

### Agent 对话与操作记录

Codex 和 Claude Code 的历史能帮助复用项目决策和排错经验，但对话也可能包含 API Key、访问令牌、路径、客户数据或未发布代码。作者提及的[Agent Memory Vault](https://github.com/mcncarl/agent-memory-vault)采用 Markdown 作为长期记忆来源，并以索引辅助检索。无论使用何种工具，长期记忆都应先经过筛选与脱敏，不能把原始会话日志自动视为适合永久保存的知识。

## 原始日志不等于长期记忆

个人上下文系统至少可以区分三类数据：

| 数据层 | 例子 | 推荐处理方式 |
| --- | --- | --- |
| 原始来源 | 聊天记录、转写、网页收藏、Agent 会话 | 保留出处和访问范围，设定保留与删除规则 |
| 工作素材 | 某项目摘要、会议行动项、主题阅读清单 | 供具体任务检索，完成后按需要归档 |
| 长期记忆 | 经确认的偏好、稳定约定、项目决策 | 写入前复核，记录来源、日期和适用范围 |

如果不分层，系统容易把一次性的设想写成长期偏好，或者把模型生成的总结误当成用户亲自确认的事实。记忆条目应允许纠错、过期和删除，而不是只增不减。

## 给 Agent 的访问范围设边界

建议先从只读和小范围开始：为每类来源单独授权，只让 Agent 搜索完成当前任务所需的内容。对涉及客户、家人、健康、财务或身份信息的记录，优先使用本地处理；若任务确实需要云端模型，再由用户主动挑选并脱敏输入。模型回答应给出引用来源或文件位置，无法找到证据时要允许它说“不知道”。

实践中可以设置几条简单规则：

- 默认只读；写入长期记忆需要用户确认。
- 搜索结果带来源、日期和置信边界，摘要不覆盖原文。
- 为原始记录和导出目录设置权限，定期检查备份与删除策略。
- 给不同用途单独配置连接器和 API Key，泄露时可以局部撤销。
- 对外发送消息、修改业务数据或执行付款等动作，保留人工确认。

## 什么时候使用 GPT88 统一模型接口

资料检索与模型调用是两层。个人 vault 可以由自己选择在本机维护；如果希望在 Agent 应用中尝试不同模型或集中管理推理 API，可以评估 [GPT88 统一模型接口](https://doc.gpt88.cc/docs/blog/ai-api-proxy-guide-2026-gpt88/)。接入前按客户端核对协议、模型可用性和计费记录，并只发送当前任务必需、且你有权提交给外部服务的脱敏片段。统一入口不会自动让私人资料变安全，也不应替代本地权限控制。
