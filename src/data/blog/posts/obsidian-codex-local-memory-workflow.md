X 用户 goan999999 在 [Obsidian 本地记忆库原帖](https://x.com/goan999999/status/2088604946552017253)中，建议用 Obsidian 保存跨项目、跨会话可复用的经验，并在任务开始时检索、结束后沉淀。该帖发表于 2026 年 8 月 15 日，属于作者工作流分享；Obsidian 本身不会自动让 Codex 读取或记住 Vault 内容，检索和写入仍需要明确的工具或操作流程。汇总入口见[五项方法索引](https://x.com/goan999999/status/2111320070651551925)。

## 记忆库解决什么问题

一次会话中的临时上下文会结束，聊天记录也不一定适合原样复用。值得留下的通常是稳定的项目约定、已经验证的排错步骤、重要决策及其理由，以及下次任务需要查找的证据位置。

本站的[记忆层设计](https://doc.gpt88.cc/docs/blog/memory-layer/)按生命周期区分当前上下文、任务状态、持久指令、自动记忆和原始证据。Obsidian Vault 可以承载其中一部分持久知识，但不能替代仓库里的 `AGENTS.md`、任务记录、源代码或测试结果。

## 一个轻量的读写闭环

### 开始任务前：按问题检索

先从当前目标提取项目名、组件名、错误特征和所处阶段，再搜索 Vault 中最相关的少量笔记。读取命中的内容后检查日期、适用版本和来源；旧结论不应因为被检索到就自动当作事实。

可以采用简单目录：

```text
vault/
  index.md
  projects/<project>/overview.md
  projects/<project>/decisions.md
  workflows/<topic>.md
  incidents/<system>/<date>.md
```

每篇笔记带上来源、验证日期、适用范围和失效条件。文件名和索引应便于搜索，不必一开始就建立复杂的标签体系。

### 任务结束后：只沉淀可复用内容

写入前问三个问题：这是否会在新会话中再次有用？是否有证据支持？是否已有更新的权威位置？只留下结论、原因、适用范围、验证证据和后续动作。一次性日志可保留在原始工件中，在笔记里存路径或链接即可。

例如，排错笔记不只写“清缓存后好了”，而是记录具体症状、环境版本、执行命令、观察到的结果以及何时不适用。这样下次检索才有判断价值。

## 不要把凭据写进 Vault

“本地”不等于只有本机可读。Vault 可能通过同步服务、第三方插件、备份软件或共享目录离开设备。不要保存 API Key、密码、会话 Cookie、私钥或可直接用于登录的令牌。必要时只记录凭据变量名和安全存储位置，不记录值。

也要定期检查同步范围、插件权限、版本控制和备份策略。若 Vault 被同步或纳入 Git，按该路径可能公开的标准处理内容。敏感故障材料应脱敏后再写入。

## 何时该更新或删除

模型版本、命令、部署拓扑和产品限制变化很快。为笔记设置复核日期或到期条件；新证据推翻旧结论时，修订旧笔记并保留变更理由，不要让互相矛盾的“经验”长期并存。找不到来源、无法复现、只适用于单次任务的信息，应删除或移到临时记录。

最后要记住，记忆的价值来自可靠召回，而不是笔记数量。一个索引清楚、证据完整、过期信息会被淘汰的小 Vault，通常比未经整理的聊天归档更容易帮助下一次工作。
