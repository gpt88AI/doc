## 这个案例能确认什么

从可见的项目摘要中，可以确认三件事：作者使用 Codex 与 Unreal Engine 进行游戏制作；目标是把两款策略/动作游戏中的经典玩法融合到一个小游戏里；作者将开发过程制作成视频，希望提供制作思路，并明确作品还有未完成的部分。

这不足以证明项目的具体玩法实现、资产来源、代码结构、Codex 提示词、迭代轮数或测试结果。下面的工作方法是基于该案例目标和 Unreal 官方文档整理出的实践建议，不代表视频中的原始操作步骤。

## 先把“融合玩法”变成可测目标

“把两款游戏融合起来”是方向，不是可直接实现的需求。开始前可以选一个最小闭环来代表核心体验，例如：玩家在一张小地图上移动，遇到敌对单位后进入一场简化战斗，战斗结果再影响地图上的状态。这个例子只是需求拆解示意，不是对视频玩法的描述。

把目标拆成可观察的验收点，能让 Codex 的每次改动都有检查依据：

1. 玩家能否完成一次移动或导航？
2. 触发战斗的条件和结束条件是否明确？
3. 战斗结果是否反馈到地图或玩家状态？
4. 新一轮游玩能否复现相同流程，或按规则产生变化？

先实现一个从开始到结束都能运行的灰盒原型，再逐步增加场景、动画、音效和复杂系统。模型生成的代码看起来完整，不等于游戏循环已经成立；需要在 Unreal Editor 中运行并实际操作验证。

## 让 Codex 按小任务修改工程

给编码 Agent 的任务应当包含当前工程背景、要改变的行为、允许修改的范围和完成后的检查方式。例如，与其要求“一次做完整个策略战斗游戏”，不如先让它检查现有项目结构，再实现一个可控的玩家移动组件，并说明如何在编辑器中验证。

比较稳的迭代节奏是：

1. 先让 Codex 阅读项目入口、相关类和当前报错，复述它准备修改的范围。
2. 每轮只指定一个可以独立验证的玩法目标。
3. 要求它列出改动文件、关键假设和需要在编辑器里手动完成的步骤。
4. 构建或打开项目，按验收点实际运行；把准确的错误信息和复现步骤交回去。
5. 确认当前版本可运行后再开始下一个系统。

Unreal 项目同时包含代码、蓝图、资源和编辑器配置。Agent 可能无法仅靠源码完整判断资产状态或编辑器运行结果。因此，任务边界应说明哪些内容由它修改、哪些需要开发者在编辑器确认，避免把未验证的实现描述成已经可玩。

## 蓝图和 C++ 按职责组合

Unreal 官方文档指出，蓝图和 C++ 没有适用于所有项目的唯一选择，很多项目会混合使用。蓝图适合快速原型、行为编排和让非程序角色参与调整；C++ 更适合集中表达复杂系统、性能敏感逻辑或需要稳定复用的基础能力。一个实用做法是先用蓝图验证玩法结构，遇到复杂度、复用或性能压力时，再把稳定部分沉到 C++，并保留蓝图可调用和可扩展的接口。

这不是要求项目必须采用某种架构。小型原型可以保持简单；只有当逻辑难以阅读、多人协作冲突频繁，或运行表现证明需要优化时，才值得增加新的抽象层。

## 把资产和代码都放进可回退的迭代

在开始密集修改之前，建立版本控制并做一个可恢复的初始提交。Unreal Editor 提供源代码控制集成，Epic 文档说明它用于跟踪代码和数据的变化并协助团队协作。提交时把一个可说明的功能或修复作为单位，并记录验证状态，出问题时更容易定位是代码、蓝图还是资源变更引入的。

每次让 Codex 修改工程后，至少检查：

- 改动是否只涉及本轮目标，是否覆盖了原有资产或配置？
- 项目能否编译或打开，输出日志里是否出现新的错误？
- 玩法是否能按验收步骤实际操作，而不只是通过静态阅读代码？
- 资源引用、蓝图节点和关卡设置是否仍然有效？
- 当前变化是否已经保存为一个可以回退的版本？

如果构建环境、编辑器或第三方资源不在 Agent 的可访问范围内，应把这些限制写进任务结果，不要把静态代码检查等同于完整试玩。

## 给一周原型设定完成边界

短周期最适合验证核心玩法，不适合同时追求完整内容、精细画面和可发布质量。可以把一周拆为几个检查点：第一天定下最小玩法闭环和资产边界；中间几天逐项实现并在编辑器里验证；最后留出时间修复阻塞问题、清理明显的临时代码，并记录仍未完成的部分。

每个阶段都应产出可运行的版本。若核心循环尚未稳定，就先暂停扩展内容；若原型只能在开发者机器上运行，也应标成开发环境验证，而不是面向玩家的发布版本。创作者对未完成状态的说明值得保留：AI 可以加快生成和修改，但项目质量仍由清晰范围、编辑器验证和持续取舍决定。
