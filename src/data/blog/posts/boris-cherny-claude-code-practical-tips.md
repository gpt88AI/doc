## 先说结论：从理解代码开始，再逐步交给它更多工作

Boris 的建议不是先背一套万能提示词，而是先把 Claude Code 当作一个能读仓库、调用工具并根据反馈继续工作的工程助手：

1. 先用代码库问答摸清项目，不急着让它直接改代码。
2. 再让它做边界清楚的小改动；大任务先讨论方案和验收方式。
3. 给它可用的工具和检查信号，让它能验证结果并据此迭代。
4. 把团队长期适用的项目背景放进共享 `CLAUDE.md`，把个人习惯和局部知识放在合适的作用域。
5. 任务稳定后，再考虑 SDK 自动化和多个隔离工作区并行。

这条路径把“敢不敢交给 AI”拆成了逐步增加授权和反馈的过程。演讲者也强调，Claude Code 是通用工具，工作流应根据团队现有 IDE、终端和工具来组合。

## 1. 把代码库问答当作入门练习

对第一次使用 Claude Code 的工程师，Boris 最推荐的起点是提问，而不是立刻生成代码。他举了几类问题：

- 这段代码在哪里被调用？这个类通常怎么实例化？
- 一个函数为什么有很多参数？这些参数是什么时候、因为什么需求加入的？
- 我本周通过 Git 提交了哪些改动？
- 某个 GitHub issue 背后的代码和历史是什么？

重点不只是搜到文件，而是让它沿着调用关系、Git 历史或关联 issue 继续调查，再把证据整理成回答。这样能较快看清工具擅长什么、哪些任务需要更多上下文，也能避免新人一上来就把未经理解的大改动交给模型。

演讲者举 Anthropic 新员工入职为例，说技术 onboarding 从过去两三周缩短到两三天。这是他对内部实践的描述，并非独立评估或对其他团队的效果承诺。他还称 Claude Code 当时不会为代码建立远程索引、代码留在本地且不会用于训练；涉及数据处理和隐私时，应以你当前使用的产品条款和官方文档为准，不能只依据演讲中的口头说明。

## 2. 先让它计划，再让它落笔

当任务从问答进入改代码，Boris 建议先让 Claude 讨论方案：列出可能做法、形成计划，并在写入前请你确认。尤其是需求大、验收标准还不清楚时，直接要求一次生成数千行代码，很容易得到“代码很多，但不是你要的东西”。

可以从这样一段简短指令开始：

```text
先阅读相关代码并说明你的理解。
在修改前给出计划、预计修改的文件和验证方式，等我确认后再写代码。
```

这不是每个小任务都必须走的仪式。一个明确的小改动可以直接做；任务越大、方向越不确定，先对齐计划越能减少返工。当前 Claude Code 的计划模式和权限行为可能随版本变化，使用时查看[官方 best practices](https://code.claude.com/docs/en/best-practices)及 CLI 文档。

## 3. 给它检查结果的办法，让它自己修到通过

演讲中最值得迁移到日常工程的一点，是给 Agent 一个能观察结果的反馈回路。Boris 举的例子包括：

- 代码改动后运行单元测试或集成测试；
- 用 Puppeteer 截图检查网页；
- 截取 iOS 模拟器画面检查应用界面；
- 根据 mock 实现界面，再看截图并进行几轮修改。

如果只说“做完这个功能”，模型缺少明确的完成信号。换成“实现后运行这些测试；若失败，检查输出、修复并重跑”，它就能围绕可观察结果继续工作。对界面任务，截图和实际运行比模型自己声称“看起来正确”更有用。

一个适合小任务的提示框架是：

```text
目标：实现 [具体行为]
边界：修改 [允许范围]，不要触碰 [禁区]
验收：运行 [测试或命令]；界面任务还要打开页面并检查截图
完成条件：报告结果和仍未验证的部分
```

演讲者提到 Claude Code 会通过编辑文件、执行 Bash 和搜索文件等工具组合完成工作；工具的授权与风险仍需要由使用者管理。测试通过也只证明相应检查通过，不等同于完成了完整人工审查。

## 4. 把常用工具接进仓库工作流

Boris 把团队工具分成命令行工具和 MCP 集成两类。一个命令行工具如果不熟，可以先让 Claude 查看 `--help`，再在本次任务中说明何时使用；如果团队会反复用到，可以把简短说明写进项目上下文。对 MCP，他演示的思路也是向 Claude 说明现有服务器和用途，让它在合适任务里调用。

演讲里的通用工作顺序可以整理为：

```text
调查问题 → 对齐计划 → 调用已有工具 → 检查实际结果 → 迭代
```

演讲还提到提交、推送和创建 PR 的自然语言请求可以被模型理解。不过这些操作会影响 Git 远端或团队流程；在真实仓库里，仍要明确授权范围并检查变更、目标分支和提交内容，不能把一句快捷说法当成免审机制。

## 5. 用 `CLAUDE.md` 保存每轮都需要的项目背景

Boris 将 `CLAUDE.md` 描述为 Claude Code 启动会话时会读取的上下文文件。他建议把经常要用的信息写短一些，例如：

- 常用 Bash 命令；
- 项目结构和关键文件；
- 架构决定和代码风格；
- 团队共享的 MCP 或其他工具用法。

团队通用的项目规则适合放在仓库里共享；个人偏好则不一定适合提交给全团队。演讲也展示了按目录放置局部 `CLAUDE.md`，以及由企业集中管理的设置，让不同作用域承载不同信息。

关键是不要把所有知识塞进一个超长文件。每轮都会加载的内容应保持简明；只对特定目录或特定流程有用的信息，放在更窄的作用域，按需提供。当前 Claude Code 对 `CLAUDE.md`、auto memory、目录规则和企业策略的具体加载行为，应以[官方 memory 文档](https://code.claude.com/docs/en/memory)为准。它们提供上下文，不自动构成强制权限边界；需要阻止某些操作时，还要使用权限设置或其他真正执行限制的机制。

## 6. 记住几个终端交互技巧，但先核对版本

演讲者还快速展示了几个当时的终端操作：

| 演讲中提到的操作 | 用途 |
| --- | --- |
| Shift+Enter | 在提示中输入换行 |
| Shift+Tab | 切换编辑接受模式；演讲称 Bash 命令仍需批准 |
| `#` | 提示 Claude 记住一条信息 |
| `!` | 在终端中运行命令并把命令及输出带入上下文 |
| Escape | 中断当前生成，然后补充或修正要求 |
| Escape 两次 | 回看先前对话；之后可恢复会话 |
| Ctrl+R | 查看完整输出 |

这张表是视频中的演示记录，不应被当作当前版本的快捷键承诺。不同终端、操作系统和 CLI 版本可能不同；开始使用前先在本机运行 `claude --help`，并查看[官方 CLI 文档](https://code.claude.com/docs/en/cli-reference)。

## 7. 把 CLI 当作可组合的自动化工具

Boris 将 Claude Code SDK 和 CLI 批处理模式描述为一种“智能 Unix 工具”：传入提示和允许使用的工具，可以要求结构化 JSON 或流式 JSON 输出，再接入现有脚本、CI 或事件响应流水线。

他举的组合方式包括：把 Git 命令输出通过管道交给 Claude 分析，用 `jq` 挑选结构化结果，或者从云存储、日志和 Sentry CLI 取数据后交由它总结。这里的核心不是某一条固定命令，而是把输入、授权工具和输出格式明确下来，先在可控范围测试，再接进自动化流程。当前 SDK 参数和行为请以[官方 Agent SDK 文档](https://docs.claude.com/en/api/agent-sdk/overview)为准。

## 8. 并行会话要配隔离工作区

最后一段讲的是进阶用户如何并行处理多项工作。Boris 观察到一些高阶用户会在多个终端或 tmux 会话里运行 Claude Code，为同一仓库准备多个 checkout，或使用 Git worktree 隔离不同会话。

并行确实可以缩短独立任务的等待时间，但前提是工作区和任务边界清楚。同一个工作目录里同时改动相同文件，容易互相覆盖或让检查结果混淆。适合先并行的通常是相互独立的调查和改动；共享文件、共同设计或互相依赖的任务，应先拆清接口，再逐步推进。视频在这里分享的是使用观察，没有提供适用于所有团队的并行数量或效率数据。

## 一个渐进式上手顺序

| 阶段 | 让 Claude Code 做什么 | 你要观察什么 |
| --- | --- | --- |
| 认识仓库 | 解释关键模块、调用路径、历史变更 | 回答是否引用了正确文件和提交 |
| 小步编辑 | 修改一个范围明确的问题 | 是否遵守边界，diff 是否符合预期 |
| 加入验证 | 运行测试、预览页面或检查截图 | 是否根据失败信号继续修正 |
| 固化上下文 | 把重复、稳定的项目事实写进 `CLAUDE.md` | 是否短而适用，是否属于正确作用域 |
| 扩展工作流 | 接入团队工具、SDK、并行工作区 | 权限是否合适，任务间是否隔离 |

这条顺序让团队可以根据实际结果逐步扩大 Claude Code 的职责，而不必一开始就追求全自动或复杂提示词。
