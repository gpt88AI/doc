## 为什么先审规则，而不是继续堆规则

项目指令和 Skill 描述会参与 Agent 对任务的判断。文件越长、触发条件越宽、同一条要求被多处重复，越容易让真正重要的约束失去优先级。目标不是机械追求最短，而是让每条规则都能回答：何时适用、限制什么、如何验证。

## 四类值得检查的内容

| 检查项 | 常见信号 | 处理方式 |
| --- | --- | --- |
| 重复规则 | 同一命令或约束出现在全局、仓库和多个 Skill | 选一个权威位置，其他地方只保留指针 |
| 过宽触发 | Skill 对很多无关任务都声称“必须使用” | 收窄到明确输入、动作或交付物 |
| 无条件扫描 | 每个任务都要求读大量背景、跑全量检查 | 改成按变更范围路由到对应文档和验证 |
| 模糊完成标准 | “检查一下”“确保质量”但没有证据要求 | 写出具体命令、输出或人工判断项 |

还要检查规则之间是否冲突：例如一处要求先询问，一处要求自主完成；一处要求全量测试，另一处要求控制成本。冲突不应由模型临场猜测，应明确优先级和适用边界。

## 用小任务验证修改

1. 先记录一个当前指令文件中的典型小任务及其实际行为，例如修正文档拼写。
2. 找出该任务读取了哪些文件、执行了哪些命令，以及哪些步骤明显无关。
3. 每次只调整一组规则：精简重复内容，或缩窄一个 Skill 的触发范围。
4. 用相同任务复跑，检查相关约束是否仍生效、无关步骤是否减少。
5. 再用一个边界案例检查风险规则，例如涉及删除、凭据或外部发布的任务是否仍会停下来确认。

这能验证规则是否更清楚，但不能单独证明 Token 一定减少。若要比较成本，应在相近任务、相同模型和相同工具条件下重复测量，并记录完成质量和返工次数，而不只看单次 Token 数。

## 建议保留的指令骨架

`AGENTS.md` 可以优先保留四类信息：

- 任务范围与仓库结构的简短入口；
- 需要时才读取的文档路由；
- 高影响动作的审批边界；
- 与变更范围匹配的验证方式和完成报告要求。

详细架构背景、教程和历史决策放到各自文档，由入口文件指向。Skill 的描述则聚焦触发条件和产出，不要把整份使用手册塞进触发文本。可参考本站的[触发规则与目录结构](https://doc.gpt88.cc/docs/blog/trigger-rules-and-structure/)和[检查清单型 Skill 的设计](https://doc.gpt88.cc/docs/blog/checklist-skill-design/)。

精简时不要删掉安全边界、数据处理要求、必要测试或用户明确授权条件。更短的指令只有在仍能产生正确行为时才算改进。
