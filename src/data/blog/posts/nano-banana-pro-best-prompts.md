写 Nano Banana 提示词时，先别堆“高清、8K、电影感”。先写清这次要完成的任务、哪些字段可以替换、哪些细节必须保留，以及看见什么才算通过；否则结果再好看，也很难进入真实项目。

你可以先把任何需求压成四项：

-   **任务**：生成、编辑、替换、修复还是组合？
-   **替换**：这次会变化的人物、商品、场景、文案或尺寸。
-   **保留**：身份、构图、材质、品牌元素、透视或其他不能漂移的部分。
-   **验收**：一眼能核对的通过条件，以及失败时只改哪一个字段。

如果画面要出现泰米尔语，先在三种文字任务中选一种：直接显示泰米尔文、使用受众已经批准的罗马字转写，或按明确层级做泰英双语。把经母语者审核的逐字原文单独放进引号，并在验收项里再写一遍。这里的 `வணக்கம்` 只作为中性的“你好/问候”排字样例，不代表某个城市、宗教、节庆或单一“泰米尔风格”。

下面的 12 张卡按生图、局部编辑、参考图与版式任务组织。先选最接近的工作，再替换方括号字段；泰米尔语任务可在任一张卡后追加专门适配器，而不必另找一份浅表词库。

路线以 2026 年 7 月 16 日的 Google 官方资料为准：简单草图可从 Nano Banana 2 Lite 开始，日常生成与边界明确的编辑先试 Nano Banana 2，密集文字、多参考图、严格版式或高拒收成本任务再考虑 Nano Banana Pro；原版 Nano Banana 主要留给旧流程兼容。

这些模板可以免费复制，但不等于 Pro 可以免费运行。Google 当前的 [Gemini Developer API 定价页](https://ai.google.dev/gemini-api/docs/pricing)没有为 `gemini-3-pro-image` 提供 Free Tier；[Gemini Apps 帮助页](https://support.google.com/gemini/answer/14286560?hl=zh-Hans)所说的 Redo with Pro 属于付费订阅入口。这不构成对价格、额度、地区或普遍可用性的承诺。

这些模板是可直接改写的起点，不是受控 benchmark。每张结果仍要逐项检查原文、保护细节和输出用途。若同一个受保护字段在两次受控尝试中重复失败，停止盲抽：补输入、只修一个字段、换更合适的路线、拆分流程，或把确定性工作交给设计工具。

## 先这样使用 12 张提示词卡

每张卡都提供六个信息：**适用场景**说明任务；**路线**给出第一条尝试路径；**提示词**可以在替换方括号后直接测试；**替换**列出本项目变量；**保留**列出不能漂移的内容；**验收**则把“感觉不错”改成可观察的通过条件。

这六项并非格式游戏。生图可以创造新环境，修图却必须同时定义“要改什么”和“其余什么不能改”；多参考图必须给每张图分配职责；带文字的海报必须提供逐字文案、阅读层级和拒收条件。任务要求不同，提示词的组织方式也应不同。

你可以先用这个通用骨架改写自己的任务：

    hljs text复制[生成 / 编辑 / 替换 / 修复 / 组合] [具体图像任务]。
    输入或参考图：[说明每张输入的作用；没有就写无]。
    场景与用途：[主体、环境、读者和使用位置]。
    构图：[景别、机位、层级、光线和视觉语言]。
    替换：[本次项目会变动的字段]。
    保留：[身份、形状、原文、版式或其他必须固定的细节]。
    输出：[画幅、放置位置和交付用途]。
    验收：[看见什么就通过；看见什么就拒收]。

Google 的[图像生成官方指南](https://ai.google.dev/gemini-api/docs/image-generation)将纯文字生图、图文编辑、迭代编辑和多参考图组合分开说明；Google Cloud 的[Nano Banana 提示指南](https://cloud.google.com/blog/products/ai-machine-learning/ultimate-prompting-guide-for-nano-banana)强调明确意图、具体视觉方向、镜头语言、正向指令和迭代。这些原则能解释下面模板为何有效，但不能证明某一模板在每张图上都会原样复现。

还有一条容易被忽略：**设置不是散文**。模型、输入文件、输出尺寸和界面支持的画幅，应在界面或 API 请求字段里选择；提示词负责创意简报、不可改动项和验收条件。把“16:9”在正文里重复三次，无法让不支持该输出的路线突然支持它。

## 当前应该选哪条 Nano Banana 路线

Nano Banana 是一个家族称呼。真正有用的问题是：这次任务先在哪条路线试最合理。

| 路线                                             | 适合先从这里开始                                         | 何时升级或切换                                             |
|--------------------------------------------------|----------------------------------------------------------|------------------------------------------------------------|
| Nano Banana 2 Lite / gemini-3.1-flash-lite-image | 大量早期草图、简单构图、低成本筛方向                     | 任务开始依赖参考图、精确文字、严格版式，或一次拒收成本变高 |
| Nano Banana 2 / gemini-3.1-flash-image           | 日常生图、边界明确的编辑，多数任务的默认起点             | 身份或商品细节反复漂移，必须逐字正确，或信息层级很密       |
| Nano Banana Pro / gemini-3-pro-image             | 精细编辑、密集文字、结构化版式、多参考图及高审核成本任务 | 实际只是简单探索，或失败根因来自错误输入而不是路线能力     |
| 原版 Nano Banana / gemini-2.5-flash-image        | 维护旧流程，或复测旧提示词记录                           | 新项目没有兼容理由时，不把它当默认路线                     |

这张表是工作量分流，不是速度或质量排行榜。首屏的访问说明只负责区分“模板可复制”和“当前 Pro 入口”，不是价格指南；精确价格、额度、地区和第三方供应商结论应分别回到对应的当前来源核对，也会独立变化。模型 ID 与路线行为以 Google 开发者文档为准；官方文档同时说明 Gemini 生成图带有 SynthID。

如果你要比较的其实是不同模型家族，而不是 Nano Banana 家族内部路线，请看单独的 [GPT Image 2 与 Nano Banana Pro 对比](/docs/blog/gpt-image-2-vs-nano-banana-pro)。提示词模板页不应该顺带承担另一个供应商选择问题。

### 把模板改成项目提示词时，先填最难拒收的部分

不要从第一行开始逐个填空。先问“哪一种错误会让这张图直接不能用”，再倒推保留项和验收项。商品页最怕商品结构或标签出错，人像最怕身份漂移，室内图最怕门窗和比例失真，活动海报最怕文案错误。这个最难拒收的部分应同时出现在输入要求、保留清单和验收句里，不能只在提示词中间提到一次。

例如，你要把商品模板用于一款有三个实体按键的音箱，不应只把 `[商品]` 换成品牌和型号。还要上传已批准参考图，把“三个按键的位置与间距”写进保留项，再把“结果中恰好出现三个按键，位置能与参考图对应”写进验收项。如果首轮多出第四个按键，下一轮只强化该几何约束，而不是同时更换背景、灯光和镜头。

再例如，你要把职业人像模板用于同一位讲师的课程封面，身份参考图负责脸和发型，品牌手册负责色彩，服装参考图只负责版型。若不分配职责，模型可能从服装图借走另一个人的脸，或把品牌手册的装饰纹样贴到衣服上。参考图越多，越要明确“负责什么”和“不负责什么”。

填写模板时可以按以下顺序完成一次最小可用版本：

1.  写一个明确动词与唯一主任务，避免同一轮既生成、又修复、又重新排版。
2.  补齐不可从文字可靠推断的输入，例如真人身份、真实商品、准确文案和固定平面关系。
3.  给每张参考图一个职责，冲突时指定谁拥有最终决定权。
4.  写出三到七项真正会导致拒收的保留细节，而不是罗列画面中所有名词。
5.  把验收写成可见事实，例如“只发生一个变化”“逐字一致”“门窗各出现一次”，不要写“效果高级”。
6.  最后再补光线、镜头、材质和氛围，让视觉方向服务任务，而不是掩盖任务条件缺口。

这套填写顺序还能控制提示词长度。提示词变长并不天然更好；每一行都应该拥有明确职责。若两行分别要求“柔和晨光”和“强烈正午硬光”，删除冲突比增加第三个光线形容词更有效。若一项要求已经由界面参数负责，例如输出尺寸，就不必在每个段落反复强调。

## 把任意 Nano Banana 提示词改成泰米尔语任务

“泰米尔语提示词”至少可能指三件不同的事：用泰米尔语给模型下指令、让画面呈现一个具体的泰米尔地区或活动、让图片里真正出现泰米尔文字。前两项不一定要求成图带字；第三项则必须把每个字符当成可拒收的交付内容。不要把三种工作压成一句“做成泰米尔风格”。

先选文字模式，再填写提示词卡：

-   **泰米尔文**：画面直接出现泰米尔字符。把母语者批准的原文单独放在引号中，要求逐字一致。
-   **罗马字转写**：用拉丁字母书写泰米尔语。不同受众未必使用同一种拼法，所以要提供已批准的完整转写和目标受众，不能让模型自行发明。
-   **泰英双语**：两种语言同时出现。分别提供两条已审核原文，并写明谁是主标题、谁是副标题、字号关系以及是否允许翻译。

下面用 `வணக்கம்` 展示精确文字字段，它的意思是“你好”或“问候”。这只是中性的排字样例，不代表 Chennai、Tamil Nadu、India、某个宗教、某种服装，也不是泰米尔文化的缩写。正式发布前，应由能流利阅读泰米尔语的人批准真实文案；看起来像泰米尔文的机器翻译不能直接成为活动或商品文案。

把下面这段适配器接在任意一张任务卡之后：

    hljs text复制[生成 / 编辑] [具体图像任务]。
    文字模式：[泰米尔文 / 经批准的罗马字转写 / 泰英双语]。
    画面中的逐字原文：“வணக்கம்”
    必须逐字符复现引号内原文；不得翻译、转写、补字、重复，
    也不得用装饰符号模仿字符。
    这行文字的职责：[主标题 / 标签 / 说明 / 不显示文字]。
    第二语言与层级：[逐字原文、主次和字号关系 / 无]。
    具体背景：[地区或侨居地、活动、受众、用途]。
    允许出现的文化细节：[已核对的服装、物件、食物、建筑、
    节庆元素、颜色或环境特征]。
    不得因为“泰米尔”一词推断宗教、种姓、政治立场、名人身份、
    婚礼关系或仪式含义；只使用上面明确提供的细节。
    保留：[身份 / 商品几何 / 已批准标志 / 逐字原文 / 版式]。
    输出：[画幅、格式和投放位置]。
    验收：泰米尔文与批准原文逐字一致，没有多余文字，
    所有受保护细节完整保留。

引号不是保证正确的魔法语法。简单单行标签或初步版式可先试 Nano Banana 2；若有多段文字、严格层级或一次错字就会造成高返工成本，可以从 Pro 开始。更适合的路线只能改善起点，不能保证泰米尔语拼写、身份或商品信息一定正确，最终仍要放大到实际交付尺寸逐字检查。

### 场景 1：泰米尔语海报或缩略图

当文字本身承载主要信息时，用这一段补丁。它适合活动海报、社交媒体缩略图、邀请函和门店公告，但每条正式文案都要先由母语者批准。

    hljs text复制为 [受众与用途] 生成一张 [海报 / 缩略图 / 邀请函]。
    泰米尔语主标题逐字原文：“வணக்கம்”
    只显示一次，逐字符复现，并作为第一阅读层级。
    不得翻译、转写、缩写、重复，也不得自行增加副标题。
    在画面顶部预留 [比例] 的清晰文字区，保持高对比和足够字距。
    场景：[具体人物或物体、动作、地点与时间]。
    文化细节：[本项目已经核对并确实需要的项目]。
    视觉方向：[色板、光线、机位、材质和情绪]。
    保留：[身份 / 活动标志 / 商品 / 标志 / 必须留空的区域]。
    输出：[画幅与投放位置]。
    验收：在实际查看尺寸下，标题与批准原文逐字一致、只出现一次、
    阅读顺序第一，且画面没有自行添加文化符号或额外文字。

双语海报不能只写“做成双语”。把第二种语言作为另一条逐字原文，再写清层级，例如“泰米尔语主标题为 100% 字号，英文译文为 45% 字号”。翻译、顺序、强调方式和换行都应由项目方决定，而不是让模型猜。

### 场景 2：泰米尔语情侣或人像编辑

真人编辑先解决两件事：你是否有权上传并编辑这张图，以及结果是否还是同一个人。“泰米尔情侣”不是完整视觉说明，也不能证明两人已婚、属于某个宗教、种姓、族群、政治群体或社会阶层。请写真实场合、地点、服装、物件和允许变化的范围。

    hljs text复制在已获得当事人许可的前提下编辑上传的人像。
    只修改 [背景 / 服装 / 光线 / 已批准说明文字]。
    保留两人的脸部结构、肤色、年龄、发际线、身体比例、表情、
    姿势、手部位置，以及人物之间的相对关系。
    具体场景：[真实地点或活动背景]。
    已批准的服装或物件：[明确且经过核对的细节]。
    可选泰米尔语说明文字：“வணக்கம்”
    若使用说明文字，只显示一次，不得翻译或增加其他词。
    不得自行添加宗教、种姓、族群、政治、婚礼、名人或社会阶层标记；
    不得改变肤色、年龄、体型或五官。
    输出：[画幅与用途]。
    验收：仍能明确认出同一批人，只发生已批准的变化，
    每项文化与文字细节都能追溯到本提示词。

如果身份漂移，先删掉泛化风格词，再加强参考图职责、脸部锚点和冻结范围；如果身份保住了但场景显得空泛，就把“泰米尔风”换成两三项经过核对的具体细节，不要用更长的刻板印象清单补救。

许可和身份保护是两份不同的检查。即使人物同意编辑，提示词仍要保护脸、年龄、肤色、体型、头发、姿势和人物关系。涉及未成年人、公众人物或已故者时，一句笼统的“已获同意”也不足以证明具体合成用途获得授权，应停下来核对适用权利和发布风险。

### 场景 3：泰米尔语商品卡或信息图

商品与信息版式同时容易出现两类错误：商品被重新设计，文案或数据被编造。每张参考图只能负责一项内容；先锁定商品，再写背景和氛围，并把每一条泰米尔语标签分别放进引号。

    hljs text复制为 [用途] 生成一张 [商品卡 / 对比板 / 信息图]。
    参考图 1 负责商品轮廓、材质、标志和包装。
    参考图 2 只负责 [色板 / 版式节奏 / 光线]。
    泰米尔语标题逐字原文：“வணக்கம்”
    其他已批准标签：[每条标签单独加引号 / 无]。
    每条原文只显示一次；不得虚构卖点、价格、徽章、成分、参数、
    脚注或译文。
    阅读层级：[标题、商品、证据、行动与保留空白]。
    保留商品轮廓、控件位置、材质边界、批准标志、SKU、数字、
    货币、单位、标签顺序和全部逐字原文。
    输出：[画幅、尺寸和投放位置]。
    验收：商品与参考图 1 一致，所有泰米尔语标签逐字正确，
    阅读顺序清楚，并且没有任何无来源的断言。

信息图不仅要校对语言，也要回到原始资料核对数字、单位和关系。字体看起来正确，不能证明内容正确；模型只能组织你提供的事实，不能成为商品规格、价格、疗效或统计数据的来源。

### 只修失败字段：泰米尔语 QA 与停止线

把成图放大到实际交付尺寸，再对照母语者批准的原文检查拼写、标点、空格、词序、漏字、多字和最终字形。泰米尔语不需要照搬英文的大小写检查。随后只改一个字段：

| 失败现象                     | 第一项修复                                                               | 何时停止或换流程                                                             |
|------------------------------|--------------------------------------------------------------------------|------------------------------------------------------------------------------|
| 字形错误、缺失、粘连或被替换 | 把审核过的原文重新粘贴为独立引号字段，缩短周围文字并扩大留白             | 同一文字连续两次受控失败：生成无字底图，再由母语者审核后用设计工具确定性排字 |
| 模型翻译、重复或添加文字     | 明确“只显示一次；不翻译、不转写、不重复、不增加文字”，删除相互竞争的文案 | 版式包含的文字块已经多到无法可靠逐项核对                                     |
| 脸或商品漂移                 | 收紧参考图职责，只列出实际发生变化的身份或商品锚点                       | 源图太弱、互相冲突，或项目没有使用它的权利                                   |
| 场景文化细节空泛或不准确     | 用本项目核对过的地点、活动、物件、服装、食物或建筑特征替换“泰米尔风”     | 无法核实文化含义，或没有权利暗示该身份与场景                                 |
| 文字溢出、层级丢失           | 减少行数，写清主次字号关系，并预留更大文字区域                           | 只有把文字缩小到实际无法阅读才能塞下                                         |

使用设计工具后加字不是“生图成功”的隐藏说法，而是一次明确的生产交接：模型提供无字视觉，母语者批准文案，最终排版文件才是交付物。公开使用前还要确认真人图片、源图、标志和活动文化细节的上传、编辑与发布权利，并记录是谁批准了最终文字与事实。

## 六个从零生图的 Nano Banana 提示词

这六类任务不要求源图，但仍然需要保留项。商品形状、空间几何、画面层级、精确文案和留白，都可能在“纯生图”里漂移。保留项不是只有真人一致性才需要。

### 1. 电影感场景

**适用场景：** 你需要一帧有明确动作、环境、机位和光源逻辑的电影剧照，而不是只有氛围词的漂亮画面。

**路线：** 先用 Nano Banana 2。只有画面还包含多参考图、困难文字或严格版式时，再考虑 Pro。

**提示词：**

    hljs text复制生成一帧电影剧照：[主体] 正在 [具体动作]，地点是 [环境与时间]。
    故事瞬间是：[刚发生或即将发生的事情]。
    使用 [全景 / 中景 / 近景]，机位在 [高度与角度]，
    呈现 [镜头感]，并明确前景、中景、背景的关系。
    主光来自 [合理光源]，阴影与色彩表现为 [具体行为]。
    情绪是 [两个精确特征]，只通过人物和环境表达，不在画面中加字。
    保留 [服装、关键道具、建筑或色彩锚点]，不得改变。
    不要增加字幕、边框、标志或无关人物。
    输出：[画幅和使用位置]。
    验收：动作一眼能读懂，主体与背景分离清楚，所有锚点完整出现。

**替换：** 主体、动作、环境、故事瞬间、景别、镜头感、光源、情绪和输出。**保留：** 连续出现的服装、主道具、建筑特征、品牌色和其他前后镜头锚点。**验收：** 看图的人能用一句话说出“谁在做什么”，且没有意外字幕或多出来的人。

“故事瞬间”通常比重复五次“史诗、电影感”更有用，因为它规定了画面必须传达的关系。如果结果很精致却像摆拍，先改动作和机位关系，不要立刻换模型。

### 2. 商品主视觉

**适用场景：** 你要做电商首图或活动主视觉，需要控制商品表面、比例、灯光和文案留白。

**路线：** 概念探索先用 Nano Banana 2；包装文字、真实商品几何或品牌审核非常严格时，从 Pro 开始更合理。

**提示词：**

    hljs text复制根据上传的商品参考图，为 [商品] 生成一张主视觉摄影图。
    参考图只负责商品的形状、材质、接口和包装比例。
    把商品放在 [表面] 上，环境为 [符合品牌的场景]，机位与裁切是 [说明]。
    使用 [主光]、[补光] 和 [阴影行为]，突出 [关键材质特征]，
    但不得改变商品本身的设计。
    在 [位置] 留出 [范围] 的干净空间，供后续排版。
    保留精确轮廓、控件位置、材质接缝、包装比例、已批准标志，
    以及文字“[已核对的原文]”。
    不得虚构接口、标签、配件、反光或商品卖点。
    输出：[画幅和投放位置]。
    验收：结果能与参考图一眼对应，原文逐字正确，留白可以直接使用。

**替换：** 商品、台面、环境、机位、光线、重点材质、留白、原文和投放位置。**保留：** 轮廓、控件、接缝、材质边界、批准标志与包装比例。**验收：** 参考图和结果必须是同一个物体，不能凭空多出功能，留白区域不能被道具侵占。

如果没有真实商品参考图，就把结果称为“概念图”，不要称为忠实商品图。再详细的文字也无法证明真实产品的接口、标签和比例正确。

### 3. 职业人像

**适用场景：** 你需要商务头像、编辑人像或环境肖像，并希望表情、服装、背景和镜头服务同一个用途。

**路线：** 虚构人物先用 Nano Banana 2；要从多张参考图保持真人身份，或画面含精确文字和版式时，用 Pro。

**提示词：**

    hljs text复制为 [人物或虚构角色] 生成一张用于 [用途] 的职业人像。
    如果上传了参考图：参考图 1 只负责身份；参考图 2 只负责 [服装或色彩]；
    忽略所有参考图中的原背景。
    表情与视线：[精确说明]。
    服装：[款式、合身程度、纹理与颜色]。
    背景：[简单环境及其景深关系]。
    镜头：[头像 / 半身 / 环境肖像]，[平视或角度]，[焦段感与景深]。
    灯光：[主光方向和软硬]，再加 [轻微轮廓光]。
    保留脸部结构、肤色、发际线、辨识特征、身体比例和批准配饰。
    不要把人美化成另一个人，不加首饰，不改变年龄。
    验收：身份稳定，表情符合用途，脸、头发和手部结构自然。

**替换：** 人物、用途、参考图职责、表情、服装、背景、景别、镜头和光线。**保留：** 身份、年龄、肤色、面部结构、发际线、身体比例和批准配饰。**验收：** 人物服务既定用途，同时没有未经要求的磨皮、改龄和饰品漂移。

“照片级真实”并不能锁定人物身份。脸变了，就加强参考图职责和身份锚点；脸没变但成片不合适，就改表情、拍摄距离或背景，不要动身份描述。

### 4. 食物编辑摄影

**适用场景：** 你需要一道菜或食材故事看起来可口，同时保持合理的层次、份量和餐桌关系。

**路线：** 先用 Nano Banana 2；如果画面同时承担精确菜单文字或复杂编辑版式，再用 Pro。

**提示词：**

    hljs text复制生成一张 [菜品] 在 [上桌或食用瞬间] 的编辑摄影图。
    清楚展示菜品结构：[层次、切面、酱汁、蒸汽、焦边或装饰]。
    使用 [盘子或容器]，桌面是 [材质]，画面只放 [两到三件辅助物]。
    机位为 [俯拍 / 45 度 / 桌面平视]，裁切为 [说明]。
    光线从 [方向] 进入，阴影 [软硬行为]，让 [关键质感] 有自然高光。
    保留定义这道菜的原料、份数、盘形，以及 [重要元素] 的相对位置。
    不要增加额外装饰、重复餐具、塑料质感或画面文字。
    验收：菜品结构可读，质感像真实食物，配件不抢主体。

**替换：** 菜品、上桌时刻、结构细节、器皿、桌面、辅助物、机位、光线和重点质感。**保留：** 原料数量、层次、份量、器皿形状、文化呈现细节和主装饰。**验收：** 食物结构合理、关键质感看得见，没有多加原料改变菜品身份。

食物图常见问题是让“好吃”替代了可见结构。说清切面、油润度、蒸汽、酥脆边缘、焦痕或酱汁行为，远比继续堆“诱人”可靠。

### 5. 室内空间方案

**适用场景：** 你需要一间几何关系合理、材质清楚、家具可用、采光可信的房间概念图。

**路线：** 单个房间从 Nano Banana 2 开始；要组合多个参考图，或必须保持平面图式层级时，再考虑 Pro。

**提示词：**

    hljs text复制生成一张 [房间类型] 的室内效果图，使用者与用途是 [说明]。
    房间尺寸和开口关系：[简述几何结构]。
    把 [主要家具] 放在 [与窗、门、动线的关系]，
    再加入 [次要家具]，但不得阻挡行走路径。
    材质：地面 [材质]，墙面 [材质]，柜体 [材质]，软装 [材质]。
    自然光从 [方向和开口] 进入，并由 [实际灯具] 补光。
    机位在 [高度与角落或轴线]，重点展示 [空间关系]。
    保留门窗数量和位置、房间比例、固定柜体与必需家具数量。
    不得制造不可能的转角、重复开口、漂浮物体或无故放大房间。
    验收：动线可走，所有开口固定，每种主要材质可区分且画面不杂乱。

**替换：** 房间、使用者、几何、家具、材质、光线、机位和重点关系。**保留：** 门窗、固定柜体、房间比例、家具数量与动线。**验收：** 这个空间在现实中可以建造并正常行走，固定开口和必需家具各出现一次。

如果首轮把房间“掰弯”，不要加更多风格词。先缩小视角、重申固定开口，再只测试一种构图变化。

### 6. 图标或标志概念

**适用场景：** 你要探索原创图标或标志方向，而不是直接取得商标审查结论或可交付的矢量文件。

**路线：** 轮廓探索用 Nano Banana 2；画面要出现精确字标或完整品牌信息板时，用 Pro。

**提示词：**

    hljs text复制为 [品牌或功能] 生成一个原创图标概念，
    用 [核心隐喻] 表达 [单一概念]。
    只使用一个主轮廓，最多 [数量] 个辅助形状，
    颜色限定为 [色彩]，背景为 [背景]。
    图标缩小到应用图标预览尺寸时仍应可辨认。
    采用 [几何 / 有机 / 单线 / 剪纸] 构造，
    圆角、线宽和负空间表现为 [说明]。
    保留核心隐喻、轮廓平衡、限定色板和标志四周留白。
    不要模仿现有商标，不添加场景样机；未提供批准字标时不要加字母。
    验收：小尺寸下无需解释即可读懂，没有多余符号或意外字母。

**替换：** 品牌或功能、单一概念、隐喻、形状上限、色板、背景和构造方式。**保留：** 核心隐喻、轮廓、限定色板、负空间和无未授权文字。**验收：** 小尺寸仍能辨认，并与给定参考方向有明显区别。

图像模型可以帮你找方向，但人工商标检索、法律判断和矢量重绘仍是后续步骤。不要因为一张概念图看起来完整，就把它当成已经通过商标与生产检查。

## 三个局部编辑与增强提示词

编辑任务的核心是界定变化范围。提示词必须同时说出源图、改动范围和冻结范围。“让它更好看”相当于授权模型重新设计你原本要保留的细节。

### 7. 只修改一个元素

**适用场景：** 你只想改一个物体、颜色、材质或局部区域，其余内容都应保持原样。

**路线：** 从 Nano Banana 2 开始。编辑区域包含文字、品牌几何或多张紧密关联参考图时，用 Pro。

**提示词：**

    hljs text复制编辑上传的图片。只把 [目标元素] 从 [当前状态] 改成 [新状态]。
    匹配原图的透视、焦深、光线方向、阴影软硬、反射、颗粒和色彩响应。
    在概念上保持其他像素关系不变，包括：
    [人物身份]、[姿势]、[商品几何]、[背景]、[裁切]、[文字] 和 [未改物体]。
    不要重新设计画面，不移动机位，不加道具，不“顺便优化”其他区域。
    验收：指定变化清楚可见；未编辑区域在位置、身份、光线和构图上仍与源图一致。

**替换：** 目标元素、旧状态、新状态和源图特有的保留清单。**保留：** 目标之外的一切，尤其是身份、机位、裁切、文字、商品几何、阴影与背景。**验收：** 你能准确说出源图和结果之间只有一个有意差别。

若要做多项无关修改，工作流允许时应依次处理。把服装、地点、季节、机位和光线一次全改，会让你无法判断究竟哪一项导致失败。

### 8. 老照片修复与画质增强

**适用场景：** 你要降低破损、噪点、偏色或曝光问题，但不能凭空创造人物身份、商品细节或文档文字。

**路线：** 从 Nano Banana 2 开始；面孔、包装或文件细节必须严格保真时，用 Pro 的结构化保留清单。

**提示词：**

    hljs text复制修复并增强上传的 [照片或扫描件]。
    修正 [灰尘 / 划痕 / 褪色 / 噪点 / 偏色 / 曝光]，
    同时保留原构图、年代、人物身份、面部结构、衣着、商品特征、
    原有印刷文字和自然材质纹理。
    只恢复源图能够支持的细节。
    皮肤、布料、纸张或材料应保留真实颗粒；
    不要做蜡质磨皮，不发明睫毛、首饰、标志，
    不制造锐化光晕，也不补写源图无法辨认的文字。
    输出用途：[展示或归档用途]。
    验收：损伤明显减弱，但仍是同一个人、物体、时刻和文献记录。

**替换：** 源文件类型、可见损伤、需要保护的历史或商品细节、输出用途。**保留：** 身份、年代、构图、服装、材料纹理、可读原文，以及缺失区域的不确定性。**验收：** 图像变干净但不像重新发明；模糊区域保持克制，不做“自信造假”。

增强无法恢复根本不存在的证据。若脸、标签或文件行无法辨认，只有在任务本身明确要求“创意重建”时，才可以把输出称为重建结果。

### 9. 同时更换服装和背景

**适用场景：** 你需要两个有边界的改动，同时保持人物、姿势、机位与身体比例不变。

**路线：** 单张源图先用 Nano Banana 2；要协调多张身份或服装参考图时，用 Pro。

**提示词：**

    hljs text复制编辑上传的人像，只做两项变化：
    1. 把 [当前服装] 换成 [新服装的版型、材质和颜色]。
    2. 把背景换成 [新环境及其景深关系]。
    保留人物身份、面部结构、肤色、头发、身体比例、姿势、手部、
    视线、机位、裁切和表情。
    新服装必须服从原姿势和原光线；新背景的透视与光向必须和人物一致。
    不要改变年龄、体型、妆容、首饰或五官。
    验收：明显还是同一个人和姿势，服装贴合自然，人物与背景共享同一套光线逻辑。

**替换：** 旧服装、新服装、材质、颜色、新环境和景深。**保留：** 身份、年龄、脸、身体比例、姿势、手部、表情、机位、裁切和未要求的配饰。**验收：** 只有服装与背景发生变化，人物像在同一个真实空间里被拍摄。

这类“双变化”仍然是可诊断的，因为两项变化彼此相关：衣服与背景都必须重新服从同一光线。如果身份也要改变，那已经是第三项改动，最好拆成另一轮。

## 三个参考图与版式提示词

参考图与版式任务的成败，取决于每个输入有没有明确职责。“参考这些图”不够具体：一张图可能负责身份，一张负责服装，一张负责构图，一张只负责视觉语言。若两个输入争夺同一细节的所有权，应在生成前解决冲突。

### 10. 保持角色一致

**适用场景：** 你希望同一个角色在新姿势、动作或场景中仍然可以被认出。

**路线：** 少量参考图先用 Nano Banana 2；参考图、道具或分镜很多且审核成本高时，用 Pro。

**提示词：**

    hljs text复制使用上传的参考图生成角色新画面，并严格按职责读取：
    - 参考图 1 负责脸、年龄、肤色和头发。
    - 参考图 2 负责服装结构、材质和颜色分布。
    - 参考图 3 只负责 [道具或姿势语言]，不负责身份。
    让角色在 [新场景] 中做 [新动作]，景别与角度为 [说明]。
    保留脸部结构、发际线、身体轮廓、服装构造、标志性色块，
    以及 [角色专属锚点]。
    允许姿势、表情、环境和机位按要求变化。
    不要混合不同脸，不借用参考图背景，不改变服装部件数量，不加新配饰。
    验收：不看参考图也能认出角色，每张参考图的职责都没有串位。

**替换：** 每张参考图的职责、新动作、新场景、景别和角色锚点。**保留：** 脸、头发、轮廓、服装构造、标志性色彩、道具身份与服装部件数量。**验收：** 审核者能把每个保留特征对应到正确参考图，没有身份或样式相互污染。

不要把“像参考图”当作完整指令。模型必须知道该像哪张图的哪一部分，也要知道哪些背景和偶然元素不能继承。

### 11. 精确文字海报

**适用场景：** 交付物本身包含文案、层级和阅读顺序，错一个字也会被拒收。

**路线：** 优先 Nano Banana Pro，因为文字与版式就是主要风险。如果你计划在图外用确定性设计工具后加文字，那是另一种工作流，可以先用较简单路线只生成底图。

**提示词：**

    hljs text复制为 [用途] 生成一张 [海报 / 活动卡 / 社交媒体图片]。
    画面只能出现以下文字，不得增加其他词：
    标题：“[精确标题]”
    副标题：“[精确副标题]”
    信息：“[精确日期、时间或行动按钮]”
    阅读层级：先标题，再看 [主视觉]，然后副标题，最后信息。
    视觉方向为 [说明]，色板 [颜色]，字体气质 [说明]，间距 [说明]。
    为 [投放位置] 保留 [安全边距或裁切要求]。
    保留拼写、标点、大小写、行序、品牌色、标志位置和阅读顺序。
    不得虚构标签、伪文字、徽章、价格或额外行动按钮。
    验收：每个字符与原文一致，在目标显示尺寸下仍能按预定顺序阅读。

**替换：** 格式、用途、完整原文、主视觉、层级、方向、色板、字体气质和投放位置。**保留：** 每个字符、标点、大小写、行序、标志位置、色板和安全边距。**验收：** 逐字核对；即使设计很好看，只要多字、漏字或错字就拒收。

精确文字生图仍需要人工校对。如果同一行反复失败，缩短生成时需要承担的文字，或改用确定性设计工具排字，而不是把错字称作“差不多”。

### 12. 信息图或多参考图组合

**适用场景：** 你要做结构清楚的信息板、对比板或多来源组合图，同时不能混淆各输入的角色。

**路线：** 当层级、精确标签和多参考图都是核心要求时，直接从 Nano Banana Pro 开始。

**提示词：**

    hljs text复制为 [受众与决策] 生成一张 [技术信息图 / 对比板 / 多参考图组合]。
    按职责读取上传素材：
    - 参考图 1：[主体或商品事实]
    - 参考图 2：只负责 [样式或色彩语言]
    - 参考图 3：只负责 [图解结构或构图]
    阅读顺序依次为 [第一步]、[第二步]、[第三步]，最后是 [决策或结论]。
    只使用这些已核对标签：“[标签 1]”“[标签 2]”“[标签 3]”。
    用 [关系、流程或对比] 解释内容，不添加未提供的数据。
    保留来源身份、批准标签、相对层级、品牌色，以及事实和示意的区别。
    不要合并参考图职责，不虚构统计，不加入装饰性结论。
    验收：受众能说出决策路径，所有标签准确，每个事实都可追溯到提供的输入。

**替换：** 格式、受众、决策、参考图职责、阅读顺序、批准标签、关系和品牌要求。**保留：** 事实标签、来源身份、层级、参考图边界、品牌色与事实/示意区分。**验收：** 阅读顺序无歧义，标签逐字正确，人工审核者能核对每一项事实。

图像模型可以组织你提供的事实，但不应该成为事实来源。发布前必须回到原始资料核对所有数字、断言与标签。

## 提示词失败时，先找责任字段

第一张结果不合格时，不要先重写整段。给失败命名，按照“任务要求优先、形容词最后”的顺序修复。

| 失败责任           | 画面表现                                               | 第一项修复                                       |
|--------------------|--------------------------------------------------------|--------------------------------------------------|
| 操作写错           | 要求编辑却重画了整张图，要求修复却重新设计             | 第一行明确使用生成、编辑、替换、修复、组合或排版 |
| 缺输入             | 没有参考图或准确原文，却要求保留身份、商品、文字或版式 | 补齐源图或引号内原文，不要用风格词补证据         |
| 保留项太弱         | 改动成功，但脸、商品、裁切或背景漂移                   | 写出冻结范围和逐项保留清单                       |
| 指令冲突           | 同时要求互斥的机位、光线、风格、文字或空间结果         | 每个字段只留一个明确要求，删除冲突               |
| 路线不合适         | 草图路线持续败在密集文字、多参考图或严格版式           | 保持同一基线，换到更适合高难要求的路线           |
| 任务不现实或不安全 | 需要伪造证据、欺骗性用途、不允许内容或无法证明的确定性 | 停止、缩小任务，或选择合法的制作方式             |

一次只改一个字段。若主体、机位、光线、色板和路线同时改变，即使结果更好，你也不知道哪项修复有效。如果遇到的是在线服务或请求错误，而非画面内容问题，请转到 [Nano Banana Pro 故障排查](/docs/blog/nano-banana-pro-not-working-fix-guide)，不要无限重写提示词。

## 用同一提示词做一次可解释测试

<img src="/docs/blog/zh/nano-banana-pro-best-prompts/img/test-worksheet.webp" class="blog-content-image cursor-zoom-in transition-opacity group-hover:opacity-90" loading="lazy" alt="对比基线与单变量版本，并做保存、改写或放弃决定的中文测试表" />

有用的提示词记录至少包含一个基线和一个受控变体。目标不是宣布“全球最好”，而是让下一次决定有解释。

1.  **冻结任务和路线。** 操作、输入文件、画幅、保留清单与验收项保持不变。
2.  **生成基线。** 用普通话记录可见失败，例如“标志字母变了”“窗户位置移动”“脸和参考图不再一致”。
3.  **只改一个字段。** 缩小编辑区域、明确参考图职责、删除冲突，或加强一条保留指令。
4.  **比较相同指标。** 只看主体、版式、受保护细节和既定验收项，不比较模糊的“总体感觉”。
5.  **做一个决定。** 通过就保存；能说清原因就只改失败字段；持续破坏保留项就放弃。

“两次失败就停”是预算边界，不是对模型能力的永久判决。两次受控失败只能说明当前的“提示词 + 输入 + 路线”组合不值得继续盲抽。此时应换输入、换路线、拆成分步流程，或改用确定性编辑步骤。

### 一次测试至少要留下哪些记录

只保存“最后成功的提示词”，下次仍然很难复现。最低限度应同时记录输入版本、路线、界面或请求设置、完整提示词、生成时间、基线失败、单次修改和最终决定。输入图若后来换过裁切、压缩或颜色，应该视为新输入，而不是沿用旧测试结论。画幅、输出尺寸等设置也要单独记录，不能假定它们已经写在提示词里。

基线失败要写成任何审核者都能重新看到的事实。例如“包装正面少了第二行文字”“左侧窗户从一扇变成两扇”“人物发际线与参考图不一致”，都比“质感不够好”有用。后者没有定位责任字段，也无法判断下一张图是否真的修复。

单次修改则要能对应基线失败。包装文字出错，就补充逐字原文与禁止额外文字；窗户数量漂移，就把门窗数量写进保留和验收；发际线变化，就收紧身份参考图职责。不要在同一变体里又换色板、又改机位、又升级路线，否则“成功”也无法说明哪一项生效。

最后的决定只有三种：

-   **保存**：变体通过全部保留项和验收项，并留下输入与路线记录。
-   **改写**：失败仍能归因到一个字段，下一轮有明确且唯一的修改。
-   **放弃**：同一受保护细节连续失败两次，或任务要求模型发明不存在的证据。

团队使用时，可以让一人负责生成、另一人只按验收项审核。审核者不需要知道哪个版本“更贵”或“更高级”，只需要检查要求是否达成。这种分工能减少对漂亮但不可用结果的偏爱，也能让后续更换路线时保留同一套比较口径。

## 通过验收后再存入提示词库

提示词库应该保存任务要求和测试结果，而不只保存最后一段文字。个人笔记、表格或生产数据库都可以使用类似结构：

    hljs json复制{
      "name": "product-hero-soft-window-light",
      "job": "商品主视觉",
      "route": "gemini-3.1-flash-image",
      "inputs": ["已批准的商品参考图"],
      "prompt": "根据参考图生成商品主视觉……",
      "replace": ["表面", "环境", "机位", "光线"],
      "protect": ["轮廓", "控件", "已批准标签"],
      "pass_check": "参考图匹配、标签准确、留白干净",
      "test": {
        "baseline_failure": "标签文字改变",
        "single_change": "引用准确原文并禁止额外文字",
        "decision": "save"
      },
      "source_note": "原创模板，不构成跨路线性能结论",
      "checked_on": "2026-07-16"
    }

除非会直接影响执行，否则不要把易变事实塞进创意提示词记录。模型 ID、路线状态、画幅支持、输出控制和 API 请求形式应该带日期与官方来源；价格、额度、免费访问、地区、隐私和商业用途条款需要各自的当前证据。公开提示词卡不能替这些事实背书。

图库、GitHub 清单、论坛帖子和视频依然值得浏览。你可以从中提取主体语言、机位描述、光线关系、编辑动词和构图思路，并保留来源链接；但点赞数、星标、精选截图和“每次都成功”的标题不能成为你的验收标准。

## 常见问题

### 这些 Nano Banana 提示词可以原样复制吗？

可以，但要先替换所有方括号字段，并提供模板要求的输入文件。模板足够完整，可以直接测试；保留项和验收项却必须适配你的项目。没有真实商品图的商品模板、没有准确原文的海报模板，都不算真正准备好。

### 修照片时，最实用的 Nano Banana 提示词怎么写？

使用范围明确的编辑指令：`编辑上传图片，只把 [目标] 从 [旧状态] 改成 [新状态]，并保留 [身份、姿势、机位、裁切、光线、背景和文字]。` 最好的第一条编辑提示词，通常是同时说清变化与冻结范围的最窄版本。

### 怎样让 Nano Banana 提升画质？

先给可见缺陷命名：噪点、曝光、偏色、划痕、模糊或压缩，而不是只写“提升画质”。然后声明哪些内容不得发明。修复任务尤其要保护身份、年代细节、材料纹理、原有印刷文字，以及不可读区域的不确定性。

### 怎样让 Nano Banana 正确显示泰米尔文？

先决定使用泰米尔文、受众批准的罗马字转写，还是泰英双语；再把母语者审核过的原文作为独立引号字段，禁止翻译、转写、重复和额外文字。像 `வணக்கம்` 这样的样例也要在实际尺寸下核对拼写、标点、空格、词序、漏字、多字与字形。密集文字版式可以先试 Pro，但它不是拼写保证；同一行连续两次受控失败时，生成无字底图，再用设计工具排入母语者批准的文字。

### Nano Banana 2 Lite、Nano Banana 2 和 Pro 应该选哪个？

日常任务先试 Nano Banana 2；大量简单草图用 Lite；逐字文字、密集版式、多参考图、品牌精度或高拒收成本由任务核心决定时，用 Pro。原版模型主要留给旧流程兼容，不作为新任务默认项。这是工作分流，不代表每个个案都存在固定胜者。

### 提示词应该写成 JSON 吗？

创意简报通常不需要。自然语言更容易阅读和迭代；应用需要命名字段、日志或可重复存储时，JSON 很有用。模型选择和受支持参数放进 API 请求，画面要求、保留细节和验收项放进提示词 payload。

### 公开的 Nano Banana 提示词库可靠吗？

它们适合作为发现入口：你可以看到提示词和作者展示的结果。但多数页面不会证明路线、隐藏设置、参考图、筛选过程和重复成功率。复制思路后，应改写成符合自己任务的完整要求并跑一次基线测试。

### 同一提示词连续失败两次怎么办？

停止盲抽。先记录重复失败，再判断能否通过一个字段、缺失输入或路线变化来解决。若不能，就放弃该模式、把流程拆开，或使用确定性编辑步骤。更多形容词不是诊断。

真正耐用的单位不是一句“神提示词”，而是一对可以共同审核的提示词与验收项：操作清楚、输入正确、变量明确、受保护细节完整、路线适合，并且结果能被明确接受或拒绝。
