## 核心是交接质量，不是模型标签

把任务拆成“先收集证据，再作判断和修改”，能减少主执行阶段反复找资料的时间。但如果搜集阶段漏掉关键约束，或把猜测写成事实，短交接包会放大误差。无论使用一个模型、多模型还是子 Agent，都要让执行者能回到原始文件和来源核验。

分阶段尤其适合：需求材料分散、需要先比较多个选项、实施前要整理复现步骤，或代码修改涉及一段明确的背景调查。纯粹机械的小改动不一定需要两轮；强耦合、需要边探索边调整判断的任务，也可能在一次连续会话里更合适。

## 一个可复用的 Task Packet

```text
目标：最终需要完成什么
现状：当前观察到的行为，以及如何复现
证据：相关文件、链接、命令和原始输出
已知事实：有直接证据支持的结论
待核实：推测、冲突信息和缺失证据
约束：不可改变的接口、目录、权限和审批边界
建议下一步：可选方案与依据，不替执行者隐瞒取舍
验收：预期行为、验证命令及通过条件
```

“1–3K Token”是原帖建议的长度范围，不是通用最优值。包应尽量短，但不能删掉复现条件、关键代码片段、证据位置、负面结果或安全约束。若内容太多，保留索引和摘要，并让执行者按需打开原始来源。

## 执行者如何使用交接包

1. 先检查目标、约束和证据是否互相一致。
2. 对关键结论回读代码或原始来源，区分事实和建议。
3. 确认缺少的信息是否会改变实现；必要时先补充检索或提出问题。
4. 实施最小范围的修改，按变更影响运行验证。
5. 汇报实际完成项、命令结果、未解决问题和仍需人工决定的事项。

这个流程能减少重复探索，但本身不保证质量或费用下降。衡量效果时可以记录从开始到有效交付的时间、重复读取量、返工率和最终成本，再比较相似任务；不要只比较交接文字长度。

## 选择执行模型时看当前能力

原帖用 Luna 和 Sol 表示轻量搜集者与主执行者，并提到特定订阅计划的额度对比。产品可用模型、路由名称、用量算法和限额可能变化。做实际路由时，以当前模型选择器和账户说明为准，先用一项小任务比较延迟、质量、工具能力和成本，再决定是否分工。

如果使用子 Agent，补上范围、可编辑目录、预期交付和停止条件；主 Agent 仍应复核输出。相关背景可参见本站的[Codex 子 Agent 分工指南](https://doc.gpt88.cc/docs/blog/codex-subagent-task-delegation/)与[Codex 多模型工作流](https://doc.gpt88.cc/docs/blog/gpt6-codex-four-core-techniques-video/)。
