把所有经验写进 Prompt，看起来像是在增加约束，实际可能让 Agent 更难判断优先级。腾讯云开发者文章的核心观点是：删除大量低价值规则，把确定性要求分别放到上下文索引、可信事实来源、工具能力和验证关卡中。

本文依据奇舞周刊第 597 期摘要整理。标题中的“删掉 80%”是来源文章的表达，不是所有项目都应该机械删除 80% 文本；真正要做的是检查每条规则应该由谁负责。

## 一、四类约束不要全部交给 Prompt

| 约束 | 更适合放在哪里 |
| --- | --- |
| 资料在哪里、何时读取 | 上下文索引和渐进式披露 |
| 哪个事实可信 | 数据源、版本和来源登记 |
| 哪些动作可以执行 | 工具 Schema、权限和运行时策略 |
| 是否达到完成标准 | 自动化测试、验收和发布门禁 |
| 需要模型判断的偏好 | Prompt、Skill 和任务上下文 |

Prompt 应该告诉模型目标、优先级和不可越过的边界；不应替代权限系统、类型检查、测试和事实数据库。

## 二、为什么超长 Prompt 会降低交付成功率

规则越多，模型越难区分：

- 哪些是当前任务必须遵守的要求；
- 哪些只是历史背景；
- 哪些规则已经被代码和工具强制执行；
- 哪些规则之间可能冲突；
- 哪些细节只有特定任务才需要。

结果可能是上下文成本变高、关键指令被稀释、模型机械执行过时流程，甚至为了满足文字要求而忽略真实仓库状态。

## 三、把规则改造成系统能力

### 上下文索引

用 README、AGENTS、Skill 入口和目录索引告诉 Agent 去哪里找资料，再按任务加载细节。不要每次都把整个项目文档塞进上下文。

### 可信事实源

给规则、配置、数据库 Schema、模型列表和产品状态设置唯一维护位置。其他文档只引用，不复制可能变化的事实。

### 工具能力

工具层可以强制参数类型、权限、预算、路径和审批。模型即使生成了越界意图，工具也不应执行。

### 验证关卡

用 lint、类型检查、测试、截图审查、API 校验、路由审计和发布探针判断是否完成。把“请认真检查”改成可执行的失败条件。

## 四、哪些规则还应该保留

不是所有 Prompt 都应该变短。以下内容通常应保留：目标、范围、优先级、不可逆风险、用户偏好、输出格式、证据要求和完成条件。删除的应该是重复、过时、已由工具强制执行、与当前任务无关的手把手过程。

## 五、精简流程

1. 把现有 Prompt 按规则逐条拆开。
2. 标记每条规则的责任方：模型、数据、工具、测试或人工。
3. 删除重复和已经自动执行的规则。
4. 把权限、Schema、预算和验证迁移到系统层。
5. 用一组真实任务对比精简前后的成功率、返工率、Token、延迟和越界事件。
6. 将失败案例回流，决定是补 Prompt 还是修系统。
