修改一个小功能时，编程 Agent 有时会先打开整份大文件，再反复搜索函数、调用点和引用关系。项目变大后，这种工作方式会带来多余的上下文和定位成本。govin.eth（G哥）在[原帖](https://x.com/goan999999/status/2112454522379304964)中分享了自己的做法：给 Codex 配置 Serena MCP，让 Agent 按函数、类和引用定位代码，并称 Token 消耗降低了 90%。原帖还附带一段约 18 秒的演示视频。

这条经验背后的核心不是“一个 MCP 会自动省掉 90% Token”，而是把代码导航从大范围文本读取，转为利用语言服务提供符号和关系信息。Serena 官方文档确实列出了符号查找、文件概览、引用查询和部分语言的符号重命名等能力；但具体节省多少取决于任务、仓库、语言服务、模型、工具调用和初始上下文。**90% 是原作者在原帖中的经验性主张，帖子没有给出测量口径或对照实验，不能当成普遍结果。**

## Serena 为 Codex 补上什么

Serena 是通过 MCP 向编程 Agent 提供代码检索、编辑和重构能力的工具。它默认使用语言服务器协议（LSP）获取项目的语义结构，例如符号、声明和引用；官方 README 说明其语言服务器后端覆盖多种编程语言。它也提供基于 JetBrains 插件的后端，但那是另一种需要 JetBrains 环境的方案。

对 Codex 而言，Serena 的价值在于补充 IDE 式的结构化导航：例如先定位 `handleRequest` 的定义，再列出引用它的符号，或者在修改前查看文件符号概览。Agent 仍负责理解任务、决定下一步和生成修改；Serena 提供的是可调用的代码操作，不会代替模型推理，也不会自动保证修改正确。

| 工作 | 纯文本搜索常见路径 | Serena 可提供的语义线索 |
| --- | --- | --- |
| 找函数定义 | 搜索函数名，再判断同名结果 | 按符号名称定位定义及其所在范围 |
| 判断调用方 | 搜索文本并逐个排除注释、测试或同名符号 | 查询语言服务器能识别的引用关系 |
| 理解文件结构 | 读文件或搜索多个关键词 | 获取符号概览，再按需读取具体实现 |
| 修改符号 | 文本替换，自己检查相关位置 | 对支持的语言进行符号级重命名或局部编辑 |

语言服务的能力因语言、依赖是否安装、项目索引状态和目标版本而异。Serena 官方文档也明确区分了 LSP 与 JetBrains 后端的能力范围；例如符号移动、完整类型层级和调试并非所有后端都提供。遇到不支持的语言或不完整的项目状态时，仍需要回退到普通搜索、文件阅读和构建验证。

## 怎样接入 Codex

Serena 官方仓库目前的快速开始路径是先安装 `uv`，再通过它安装 Serena 并初始化：

```bash
uv tool install -p 3.13 serena-agent
serena init
```

Serena README 推荐 Python 3.13 作为安装环境；项目当前的 `pyproject.toml` 声明支持 Python 3.11 到 3.14。安装前应以[官方安装文档](https://oraios.github.io/serena/02-usage/010_installation.html)的当前要求为准，并查看安装器实际要执行的动作。

Serena 的 Codex 客户端说明提供一条快捷配置命令：

```bash
serena setup codex
```

当前官方实现会调用 `codex mcp add serena -- ...`，把 Serena 注册为 MCP 服务。运行前先检查已有配置：

```bash
codex mcp list
```

如果列表中已经存在名为 `serena` 的服务，不要直接重复运行快捷配置命令；Codex 的 `mcp add` 对同名服务会更新配置。先审查 `~/.codex/config.toml` 中该条目，并确认其传输方式、启动命令、环境变量和项目范围，再决定是修改现有条目还是为新配置选用另一个名字。Serena 安装文档和实现可以帮助判断默认设置，但不能替你理解本机已有配置的用途。

手动配置时，Serena 当前文档给出的示例是：

```toml
[mcp_servers.serena]
startup_timeout_sec = 15
command = "serena"
args = ["start-mcp-server", "--project-from-cwd", "--context=codex"]
```

这是一个配置片段，不要把它覆盖写入现有 `config.toml`。如果文件里已经有 `[mcp_servers.serena]`，应合并或调整该表；保留其他 MCP、模型和环境设置。Codex 官方文档指出，CLI、桌面应用和 IDE 扩展共享 Codex MCP 配置；项目级 `.codex/config.toml` 则适用于受信任的项目。

连接后可以在 Codex 的 `/mcp` 菜单中确认 Serena 是否启动、工具是否可用，再用一个只读的小任务检查符号概览、定义和引用结果是否对应当前代码。Serena 的客户端文档还提醒：Codex App 未必以仓库目录作为会话工作目录，因此可能需要在会话开始时让 Codex 激活当前项目。若 Serena 找错目录、找不到符号或语言服务未就绪，先检查当前项目路径和 Serena 日志，而不要立即把检索结果当作代码库事实。

## 用在什么任务上更合适

Serena 更适合需要理解代码结构和跨文件关系的任务：追踪一个 API 从路由到服务层再到存储的调用链、梳理类和函数的引用、分析重构影响范围，或修改一个涉及多个调用点的符号。此时先查询符号，再只读取相关实现与测试，通常比一开始打开多个大文件更容易控制上下文。

简单的单文件修改、配置编辑、文档任务和短小的代码问题，现有 Agent 搜索工具往往已经足够。额外 MCP 服务也会带来启动时间、工具选择成本、索引与语言服务器依赖；工具数量和工具描述本身也可能增加 Agent 需要处理的上下文。因此，可以按任务类型决定是否启用，避免把“工具更多”误当成“任务更省”。

Serena v2 还提供两种 Agent 接口：常规模式下每项操作是独立 MCP 工具，REPL 模式则让 Agent 通过一个工具组合调用。选择哪一种要看客户端兼容性、操作可审计性和工具输出；它们并不会自动改变模型对整个任务的上下文预算。

## 怎样验证 Token 是否真的减少

如果要验证“省 Token”，先用同一仓库版本和相同需求分别运行“Codex 默认工具”和“Codex + Serena”。尽量固定模型、推理等级、任务要求和验证标准，重复多次并记录：输入/输出 Token、工具调用次数、耗时、完成质量、遗漏和返工。再分别测量小改动、跨文件追踪和符号重构，不要只选最适合 Serena 的单一任务。

尤其应区分几类成本：MCP 工具定义与会话初始上下文，真正执行任务时读入的代码内容，以及最终因为遗漏产生的返工。Serena 可能减少重复打开文件的次数，也可能因为额外工具描述、初次索引或一次不准确的符号检索增加开销。适合团队的评估问题不是“能不能降低 90%”，而是对哪些任务、哪些语言和哪些仓库规模，质量不下降时的总 Token 与完成时间更低。

## 权限与安全注意事项

MCP 服务通常以本机进程启动，并可能使用客户端提供的文件或命令能力。安装之前要审阅官方来源、依赖与配置；接入后确认它指向的是预期仓库，避免在含有机密或重要数据的目录里运行不熟悉的工具。不要把敏感资料、访问令牌或私有客户代码写进公共配置和日志。

Serena 可以协助编辑代码，但跨文件重命名、符号删除和插入仍会改变项目内容。先让 Agent 说明计划和影响范围，保留版本控制基线，执行后查看 diff 并运行与改动相关的检查。遇到生成代码、动态调用、反射、宏或语言服务器不理解的构造时，符号图不一定覆盖所有运行时关系，应同时检查文本引用、测试和真实调用路径。

## 小结

Codex 负责理解任务和写代码，Serena 为它补充符号级导航和编辑能力。这种搭配适合结构复杂、调用关系多、文本搜索容易噪声较大的代码库；是否更省 Token，要在自己的仓库和任务上测量。先只读验证连接和定位质量，再逐步用于修改，并把配置差异、变更 diff 和测试结果都纳入复核。

若你希望对本地代码证据做二次整理，可以使用 GPT88 的统一大模型接口总结符号关系、列出需要人工复核的调用路径，或把实验记录按统一格式归纳；接入方式见[Chat Completions API 文档](/docs/api/chat-completions/)。上传模型前先确认代码和日志允许发送，并脱敏凭据、个人信息及客户数据。模型生成的关系总结仍需要回到仓库和测试中核验。
