## 自动化的目标，是让人少守几个窗口

常见的 Agent 使用方式是：人打开 Claude Code 或 Codex，交代任务，盯着执行，验收后再下一个任务。模型虽然能做很多事，但所有工作的起点仍是人；人不打开窗口，事情就不动。于是并行能力最终还是受人的注意力限制。

作者把 Agent 自动化的目标概括为“领导力”：不是让模型接管一切，而是把触发任务的起点从人手动下令，转成定时任务、Webhook、消息、邮件、告警或代码变更等事件。Agent 先按规则处理能自主完成的部分，只有需要人判断的结果才汇总上来。

这个视角改变了系统的核心问题。重点从“哪个模型更强”转向：事件怎样进入系统、谁来处理、怎样避免重复执行、什么情况下需要人工批准，以及怎样确认变更真的交付。

## 一、事件中台：统一触发、路由和结果

系统的中心是一个独立的自动化服务。作者将定时任务和实时事件都接入同一中台，由它统一分派给 Agent，再收集执行结果；确实需要判断时，才通过飞书卡片通知本人。

### 事件要先变成统一格式

事件来源可以很杂：Webhook、飞书消息、邮件、线上告警、用户反馈、GitHub PR，或定时扫描的结果。若每种来源都单独写一套接入脚本和唤醒逻辑，数量增长后就很难管理。

作者的做法是先把事件压缩为统一信封：

| 字段 | 用途 |
| --- | --- |
| 来源 | 事件由哪个产品、系统或渠道产生 |
| 类型 | 说明属于反馈、告警、PR 等哪种事件 |
| 对象 | 标识事件针对的用户、项目或资源 |
| 摘要 | 用一句话说明发生了什么 |
| 原始链接 | 回到原系统查看上下文和执行结果 |

中台收到事件后查路由规则，例如按类型选择仓库、Skill、Agent、模型和推理档位。作者把这些规则放在 `rules.json` 中。新增一种事件时，目标是添加配置，而不是再复制一套调度服务。

### 让内网 Agent 主动领任务

作者的开发 Agent 运行在家里或办公室的 Mac 上，设备位于内网，外部服务无法直接连入。他采用反向连接：Mac 上的接单程序主动向中台长轮询，等待时间结束后继续请求；中台有任务就由在线 Worker 领取。

这种方式避免把个人电脑直接暴露到公网，也让外部 Webhook 能通过中台间接触发内网任务。实际部署仍要补齐 Worker 身份认证、请求签名、访问控制、超时与重试策略；长轮询本身并不等于安全边界。

### 去重、并发和任务记录

网络重试、同一反馈追加信息、多个系统重复告警，都可能让同一事件到达多次。如果每次都新开 Agent，可能产生并发修改或重复操作。中台因此负责去重和并发限制。作者举例，某类反馈每条单独运行，同一条同时只运行一个，最多并行三条。

每次执行还应留下事件来源、分派对象、运行会话、输出和最终处置等记录。这样既能追溯“谁处理了什么”，也能观察哪些规则经常失败、哪些任务耗时较长，为后续调整模型与流程提供依据。

## 二、Agent 执行：规则驱动的模型分工

作者并没有让一个 Agent 处理所有事情，而是按任务类型分配执行者和模型：复杂开发任务由主力编程 Agent 处理，运维告警和例行检查交给另一模型，浏览器操作则交给擅长电脑控制的模型。路由目标是能力、延迟和成本之间的平衡，而不是把所有任务都交给单一“最强模型”。

这些具体型号和订阅组合只是作者在原文发布时的配置快照。模型能力、产品套餐和价格会变化；读者应根据当前可用的模型、任务约束和预算重新评估，不要直接照抄作者的成本结论。

### 把任务步骤沉淀成 Skill

原文把 Skill 视为 Agent 可执行的 SOP：将任务规则、参考资料、脚本和验收要求放到独立文件中。调度层只需说明使用哪个 Skill，修改流程时改 Skill，而不必把每一种业务逻辑硬编码进中台。

拆分后边界更清楚：

- **事件中台**决定何时触发、由谁处理、并发多少、何时升级给人；
- **Skill**说明这类任务的步骤、上下文和完成标准；
- **Agent/模型**根据任务内容完成推理和操作；
- **CI 与权限系统**负责验证和限制哪些操作可以落地。

Skill 不是权限隔离机制。若任务可能访问生产数据、修改代码或发出外部消息，仍需由运行环境和凭证权限控制其实际能力。

## 三、本地执行：权限留在自己掌控的设备上

作者把主要自动化任务放在常开 Mac 上，因为代码仓库、发布权限、飞书身份和已登录浏览器都在自己的设备里。原文给出的理由是：复制这些登录态和权限到多个云端环境，既增加维护负担，也扩大凭证暴露面；部分本地网页任务在远端浏览器里也不稳定。

这是一种特定环境下的权衡，并不意味着本地设备天然更安全。内网 Worker 同样需要最小权限、隔离执行、审计日志、凭证保护和及时更新。作者对代码 CI 采用临时虚拟机：每个任务使用新环境运行，结束后清理执行身份和虚拟机，避免 Agent 提交的代码直接在日常主机上执行。

更稳妥的原则是根据数据和权限边界选执行位置：

1. 只读、低风险任务可在受限 Worker 中自动运行；
2. 会写代码或修改数据的任务应使用隔离环境和短期凭证；
3. 可触达生产环境的 Agent 不应同时拥有不必要的浏览器登录态、密钥和管理员权限；
4. 任务失败或 Worker 失联时，要能暂停、撤销凭证并查明任务是否已执行。

## 四、CI 中台：把“写完”与“上线”拆开

原文里，开发 Agent 的工作止于提交代码并创建 PR；审查、检查、合并、发布和核实由 CI 流程完成。其关键不是自动化上线本身，而是建立一条有门槛、有记录、能确认结果的交付链。

作者描述的流程分为五步：

1. **独立审查**：由另一个 Agent 只读检查 PR，专注于可能导致真实问题的缺陷。作者报告审查最多三轮，以减少无限挑错。
2. **自动检查**：运行类型检查、测试、构建及项目硬性规则。某项失败就不能继续。
3. **受保护合并**：只有审查和检查通过，GitHub 规则才允许合并；编写代码的 Agent 不直接获得绕过门槛的能力。
4. **隔离发布**：合并后由独立发布 Worker 执行发布任务，而不是在开发环境里直接上线。
5. **线上核实**：等待发布流程结束后，检查线上版本是否确实包含本次变更，并把结果写回任务记录。

原作者称，他的项目在 2026 年 10 月合入了大量 PR，且本地 CI 使流程速度和成本得到改善；他还分享了近两周的审查数量与修复数量。这些数字来自个人项目和特定硬件，缺少外部审计，不能直接用于估算其他团队的吞吐量或节省金额。

对实际团队而言，应该先守住三个独立条件：Agent 不能自审自批，检查失败不能合入，发布后必须验证实际线上状态。速度指标只有在这些条件满足后才有意义。

## 五、飞书审批：把人工注意力留给高影响决定

执行结果统一回到飞书卡片。卡片不只是通知，还携带 Agent 的建议；人作出决定后，等待中的任务收到结果并继续执行。这样可以避免每个 Agent、脚本或机器人都直接推送消息。

作者说自己经历过一天收到几十条通知，因此把必须询问的范围缩到高影响操作：删除数据、停服、产生费用、对外发消息、改变产品方向、新建或轮换密钥、修改权限等。其他在既有规则内且可回滚的任务尽量自行完成。

这套审批机制还维护两份决策记录：一份记下已确认的决定及日期，另一份记下明确拒绝、以后不再重复询问的事项。它们让 Agent 能沿用先前的边界，减少重复打扰。需要注意，决策记录应可审阅、可撤销，并标明适用范围；旧决定不能自动覆盖新的风险或业务变化。

作者仍将用户反馈留给自己先读，再挑选值得处理的反馈交给 Agent。这个例子提醒我们：哪些信息值得保留人的判断，本身也是系统设计的一部分；自动化不必追求把每个输入都机器化。

## 一套可以逐步落地的顺序

把完整系统一次搭出来成本很高。更现实的路径是先围绕一个重复、边界清楚的任务建立闭环：

1. 选一个低风险来源，例如定时生成内部摘要；定义事件格式和原始链接。
2. 为该事件配置单一路由与专用 Skill，先只读运行并记录输入、输出、耗时和错误。
3. 加入幂等键、去重、并发上限、超时和可重试状态，确保重放不会重复产生副作用。
4. 将需要写入的操作放进隔离环境，并给 Worker 最小权限；将删除、付费、对外发送和权限变更列为人工确认项。
5. 若任务涉及代码，增加独立审查、自动测试、受保护合并和发布后核实。
6. 稳定后再接入新事件和新模型。每加一类任务，都检查它是否真的能复用现有路由、审批与审计规则。

系统是否成功，不只看“少写了多少代码”或“用了多少 Agent”，还可以观察：人工需要介入的比例、重复任务率、失败恢复时间、越权尝试数、线上变更核实率，以及从事件进入到可靠闭环的时间。

## 结语：调度系统管理的是注意力和风险

这篇分享最值得借鉴的不是某个具体模型或某台 Mac，而是把任务从单个聊天窗口拆成一条可观察的流程：事件触发，规则路由，Agent 执行，独立验证，必要时由人决策，最后核实结果并留下记录。

它也带来一条清晰边界：让 Agent 自主推进重复、可验证、可回滚的工作；让人负责模糊目标、高影响副作用和无法自动证明正确的决定。Agent 越能行动，权限隔离、审批规则、失败恢复和事后审计就越重要。
