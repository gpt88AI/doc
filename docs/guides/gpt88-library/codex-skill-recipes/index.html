3 个可复制的 Codex 实战 Skill

三个完整 Skill 模板：Bug 排查、代码审查与发布说明，含调用示例与验证方法。

适用范围：涉及账户、Key、模型、计费或接口的内容，请以 GPT88 当前控制台和对应 API 文档为准。

返回教程库

GPT88 使用说明 模型名、版本、默认值和平台入口可能随客户端版本变化，请按 GPT88 当前模型目录和客户端显示核对。

快速开始 · 模型导航 · GPT88 API Key 管理

下面三个模板分别处理问题定位、改动审核和发布说明。它们都是纯说明型 Skill，不依赖额外脚本；每个模板都有清楚的触发条件、工作范围和交付格式，适合先在练习仓库测试，再按团队习惯调整。

如果还没配置 Skill，请先完成 Skills 入门。把三个文件分别保存到 .agents/skills/bug-triage/SKILL.md、.agents/skills/review-checklist/SKILL.md 和 .agents/skills/release-notes/SKILL.md。不要把三份 YAML 合并到同一个文件。

模板一：Bug 定位与复现

适合“现象已经明确，但原因还不清楚”的任务。它先收集证据并提出最小修复方向，是否直接修改由用户当前任务决定。完整内容如下：

---
name: bug-triage
description: 用户提供报错、异常行为或失败测试，需要定位原因、整理复现步骤或分析修复方案时使用。不用于新增功能或泛泛介绍项目。
---

# Bug 定位

1. 提取当前行为、预期行为、复现步骤和环境信息。
2. 阅读报错涉及的代码、调用位置与已有测试。
3. 使用项目已有方式尝试复现；无法复现时记录缺少的条件。
4. 区分已观察到的事实和原因假设，引用文件或命令输出。
5. 提出范围最小的修复方向及验证方式。
6. 用户已要求修复时，实施相关修改并重新执行复现与必要检查。
7. 输出「现象」「复现结果」「根因或假设」「修复与验证」。

不要编造报错或通过结果。不要在输出中暴露凭证；引用日志时脱敏。

在 Codex CLI 或 IDE 对话中调用：

$bug-triage 设置页点击保存后提示成功，但刷新后选项恢复原值。请定位并修复，保持接口格式不变，并验证刷新后的持久化结果。

练习时补充真实路径、启动方式和复现步骤。验收重点是能否说明根因证据，以及修改后是否重新验证同一问题。更完整的任务写法见修复实战。

模板二：以真实问题为重点的代码审核

适合提交前检查工作区、分支差异或指定提交。该模板默认生成审阅意见，避免审核任务顺带改写代码。

---
name: review-checklist
description: 用户要求审核代码改动、检查提交风险或进行提交前评审时使用。用于寻找有证据的正确性与回归问题，不用于自动改写代码或统一格式。
---

# 代码审核

1. 确认审核范围：未提交改动、指定提交或相对指定分支的差异。
2. 范围不明确时先检查仓库状态；无法推断时向用户说明需要的范围。
3. 阅读 diff 及必要上下文，检查输入边界、错误处理、状态变化和兼容性。
4. 查看相关测试是否覆盖关键行为；不要把猜测描述为确定缺陷。
5. 仅报告可解释触发条件和实际影响的问题，给出文件位置与修复方向。
6. 按影响排序输出「问题」「触发条件」「影响」「依据」「建议」。
7. 未发现可确认问题时明确说明，并列出本次审核覆盖范围和验证限制。

默认只输出审阅结果。仅在用户另行要求修复时修改文件。

调用示例：

$review-checklist 审核当前未提交改动，重点检查空数据、重复点击和接口失败。先给出有证据的问题清单。

用包含已知小缺陷的练习分支测试它。验收时查看发现是否能复现、位置是否准确、是否把风格偏好误报成故障。“没有发现问题”不代表绝对安全；仍需运行相关测试并查看实际行为。详见代码审核实战。

模板三：生成发布说明草稿

适合把工程变更转换为用户能读懂的更新说明。用户需要指定比较范围；下面模板保留缺少信息时的确认步骤。

---
name: release-notes
description: 用户要求根据 Git 改动编写发布说明、更新日志或版本摘要时使用。用于生成本地草稿，不负责发布版本、推送代码或发送公告。
---

# 发布说明

1. 确认版本范围或比较基准；缺少时说明需要的分支、标签或提交范围。
2. 阅读范围内的提交和 diff，核对用户可见行为是否实际改变。
3. 按「新增」「修复」「升级注意事项」组织内容，没有内容的分类可省略。
4. 使用面向用户的语言，不仅复述文件名和内部实现细节。
5. 仅记录有依据的变化，不编造性能数字、兼容承诺或验证结果。
6. 输出发布说明草稿和待确认事项；用户指定文件时写入该文件。
7. 附必要的提交或文件引用，方便维护者复核。

这是草稿生成流程；不代表获得了发布、推送或向他人发送消息的授权。

调用示例：

$release-notes 根据当前分支相对 main 的改动生成发布说明草稿，保存到 docs/release-notes-draft.md，面向网站普通用户。

请把 main 换成真实基准分支。逐条检查说明能否对应到实际改动，尤其核对破坏性变化和升级步骤；不能从 diff 确认的内容应列为待确认。

如何维护这些模板

每个模板至少测试一条匹配任务、一条不相关任务和一种缺少输入的情况。根据误触发情况调整 description，根据输出缺陷改正文步骤。项目通用命令和规范继续放在 AGENTS.md，让 Skill 聚焦具体流程。

模板会使用当前客户端实际提供的工具和权限；本身不安装依赖、不增加访问权限，也不保证能执行网络或外部系统操作。涉及真实凭证或生产操作时，遵循当前用户授权和项目要求，不把秘密写入 Skill 或示例日志。
