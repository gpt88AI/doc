Codex 节省 Token 实战：减少无效上下文与返工

减少无关上下文、重复检索与无效重试，合理控制输出、推理与并行；附可复制提示词及 Token 与费用核对方法。

适用范围：涉及账户、Key、模型、计费或接口的内容，请以 GPT88 当前控制台和对应 API 文档为准。

返回教程库

GPT88 使用说明 模型名、版本、默认值和平台入口可能随客户端版本变化，请按 GPT88 当前模型目录和客户端显示核对。

快速开始 · 模型导航 · GPT88 API Key 管理

节省 Token，先从缩小任务范围、提供准确信息、减少重复操作做起。目标是用更少的总消耗交付通过验收的结果，而不是把提示词删到含糊不清。

本文适用于日常编码、排错与 Skills 工作流。ChatGPT 会员额度与 API 按量计费属于不同体系；通过本站 API 使用 Codex 时，请以本站用量日志、模型价格和计费规则为准。本文不承诺固定节省比例。

先分清：Token 少、回复短、费用低是三件事

项目包含什么应该怎么看
输入 Token指令、历史消息、代码、工具结果等提示词短，不代表整个请求短
缓存输入命中可复用前缀的输入仍属于输入 Token，命中不等于免费
输出 Token回答、工具调用参数及推理等屏幕上的回复字数不能代表全部输出
推理 Token模型内部解决问题的计算过程通常不可直接看到，计入输出用量

在官方 Responses API 的用量字段中，缓存已包含在输入总量里，推理已包含在输出总量里，不要重复相加。缓存读写价格和适用条件可能因模型、接入服务不同而变化，核对实际扣费比只看缓存命中率更可靠。

八个马上能用的习惯

1. 一次写清范围和验收

“优化项目”容易扩大工作量。换成“修复设置页保存后刷新丢失的问题，保持接口不变，复现步骤通过并运行相关测试”。写明目标、入口、边界和验收条件，通常能少走几轮猜测与返工。无需把所有实现步骤都规定死。

2. 给路径和关键报错，资料按需补充

提供相关文件路径、函数名、复现步骤、首个错误和附近堆栈。日志很长时，先给关键片段与完整日志位置，让 Codex 按需读取。不要反复粘贴整个仓库、构建产物或同一份长日志；也不要删掉定位问题必需的上下文。

3. 精简 AGENTS.md，Skills 按任务加载

AGENTS.md 适合放长期有效的项目约定、常用命令和关键限制。避免塞入历史聊天、全部接口文档或重复规则。专题细节放到参考文件，并写清何时读取。

Skills 会先展示名称与描述，使用时再读取完整 SKILL.md。把每个 Skill 聚焦到一种工作，描述写准，详细资料按需引用；不要要求每次任务都读取全部 Skills。可结合项目指令教学和Skills 入门整理。

4. 要简洁结果，保留必要验证

可以要求“最终只列改动、验证结果和遗留问题，不重复整份代码”。这能减少冗长的可见输出，但不保证内部推理同比减少。照常执行与改动匹配的测试和仓库必需检查；不要靠跳过验证、放宽危险操作权限来省额度。

5. 失败后带新证据，避免原样重试

报错后补充失败命令、关键输出和最近改动，要求先判断原因。不要连续发送“再试一次”。已有检索结论和通过的检查可以复用；只有代码变化、新失败或未解决风险出现时，才补做相应检查。排错范围应随证据逐步扩大。

6. 小任务不必盲目并行

改一处文案或修一个清楚的小 Bug，单个 Agent 往往足够。多 Agent 适合能独立开展的探索、审查或实现；每个子 Agent 都会消耗模型调用与工具上下文，协调也有成本。并行可能更快，总 Token 却可能更多。大任务按职责拆分，避免多个 Agent 重复读同一批文件，详见子智能体与并发。

7. 按任务选择推理强度

如果客户端和模型提供推理强度选项，明确的小改动可先尝试较低档位；涉及复杂依赖、数据迁移或难复现的问题，应保留足够推理。官方说明较低 effort 倾向更快、Token 更少，但具体档位和效果取决于模型。比较的是“通过验收的总成本”，低档反复返工未必便宜。

8. 同任务继续，换任务带摘要新开

同一问题的连续修改通常适合留在原聊天，复用已有决定与证据。目标已经变化，或旧上下文大多无关时，先整理交接摘要，再开新聊天。

长会话可能反复携带历史；保留会话也不保证命中缓存。压缩能减小后续上下文，但会改变可缓存前缀，还可能需要补查资料。不要把“新开聊天”或“压缩一次”当作必然降费开关，按实际完整任务记录比较。

三份可复制提示词

低消耗编码

目标：修复 [具体行为]。
入口：[相关路径/函数]；复现：[步骤]。
范围：保持 [接口/数据结构] 不变，不扩展无关功能。
验收：[预期行为]，运行相关测试及仓库必需检查。
先读相关指令和入口，只有发现依赖时再扩大检索。
这个小任务优先单 Agent；需要拆分时说明独立工作内容。
最终简述改动、验证结果和未解决项，不重复输出完整文件。

带证据排错

失败命令：[命令]；关键错误：[片段]。
完整日志位置：[路径]；最近变更：[摘要]。
先根据证据定位原因，再做最小必要修改。
不要无变化重复同一操作；失败时记录新线索并调整下一步。
修复后重跑复现步骤及相关检查，保留关键结果。

长任务交接

请整理可交给新聊天继续的简短摘要：
目标与验收条件；工作目录、分支与当前改动；
已确认结论及依据路径；已运行检查及结果；
剩余问题、失败尝试与下一步；必须保留的约束。
保留关键事实，不复制长日志，不把猜测写成结论。

怎么验证真的省了

选同一个可重复的小任务，用相同代码起点、模型、验收标准和测试环境做对照。每次只改一个因素，例如提示词范围或推理档位，分别记录全任务结果，而不是只比较最后一条回复。

  • 记录所有请求的输入、输出、缓存用量；可用时单列推理和缓存写入信息。
  • 包含失败重试、子 Agent 和交接摘要的消耗，避免漏算或重复汇总。
  • 同时记录实际费用、完成时间、验收是否通过，以及是否需要人工返工。
  • 区分首次运行与已有缓存的运行，少量重复后看稳定表现，不拿单次波动下结论。 客户端没有完整用量时，以本站日志为准；某字段未展示不等于它为零。先改最常发生的浪费，再保留效果稳定的工作方式。刚开始使用 Codex，可先读实战学习路线。
