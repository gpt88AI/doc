主动服务的 Agent：把决策、验证和停止做成一个闭环

AI工具指南2026-11-199 মিনিট পড়ুনAI AgentAgent 工程主动服务决策系统自验证RSI

本文根据 Barret 李靖在即刻的原帖整理。页面公开的结构化数据记录：作者为 Barret 李靖，原帖发布于 2026 年 11 月 14 日（北京时间），主题为“工程师的日常”。下文先复述原帖观点，再给出工程化解读；文中没有把它扩展成某个产品已经具备这些能力的证明。

如果 Agent 只是在收到明确指令后给出一次回答，错误通常还能由人及时发现。主动服务的 Agent 则要在信息不完整、环境持续变化的情况下自行决定下一步：要不要继续探索、是否执行、是否改目标，以及什么时候应该停下来请求人介入。决策一旦偏离，后续工具调用可能只是把成本继续放大。

原帖的核心提醒是：主动服务的 Agent 不只需要更强的推理，还需要管理决策依据、验证行动结果，并且知道何时停止。

原帖提出的四类能力

1. 在问题暴露前开始维护决策依据

作者建议让 AI 在问题早期，甚至预防阶段就开始决策和产出，并持续维护决策依据与结果。这样，问题真正暴露时，Agent 可以把新增信息补回已有记录，快速修正原来的判断，而不是从零开始重跑。

这意味着 Agent 的状态不能只是一段对话历史。至少应该能回答：

  • 当时知道了什么？
  • 哪些判断仍然只是暂定假设？
  • 已经采取过哪些行动，结果是什么？
  • 哪一条新证据触发了修正？

对工程系统来说，这是一份可更新的决策记录。它既保存结论，也保存结论的依据和不确定性。

2. 沿不同决策路径做分支推演

第二类能力是“所见即所得”：系统能够沿着不同决策路径进行分支推演，直观呈现每条路径的收益、成本和风险，减少真实执行中的无效尝试。

重点不在于让模型多写几段分析，而在于把候选行动变成可以比较的对象。例如，在修改一个生产配置前，系统可以分别估算直接修改、先做小范围试运行、暂缓并收集更多信息三条路径的影响，再把选择依据留下来。

如果分支推演不能显示假设、代价和失败条件，它就容易变成一组看起来合理的文字，而不是能够帮助决策的工具。

3. 随目标和环境变化动态调整

主动服务 Agent 面对的目标不是一次性输入。环境变化、资源限制和新证据都可能改变原来的条件，因此系统需要动态更新目标、决策条件和执行逻辑。

这里有两个容易被忽略的动作：

  1. 调整：新信息出现后，重新计算下一步，而不是机械执行旧计划。
  2. 终止：当前行动已经偏离目标，或者继续执行的风险超过收益时，主动结束这条路径。

“持续运行”不应该被当成默认的成功标准。一个能够及时停下来的 Agent，可能比一个不断尝试的 Agent 更可靠。

4. 用自验证和低成本反馈检查执行

第四类能力是给决策和执行建立自验证环境：持续比较实际结果和预期目标，发现偏差后修正决策。必要时，再通过简洁的交互反馈让人参与关键决策。

这条链路可以拆成四步：

预期目标 → 执行动作 → 实际结果 → 偏差判断与修正

自验证不是让 Agent 自己宣布“完成”，而是让它提供可核对的证据：目标是什么、实际发生了什么、差异在哪里、下一步为什么这样改。人工介入也不应变成重新阅读全部日志，而应该只收到少量、明确、可选择的问题。

把四点合成一条执行闭环

将原帖的四类能力串起来，可以得到一个适合工程实现的最小循环：

观察环境
  ↓
更新决策记录与目标
  ↓
生成并比较候选路径
  ↓
选择：探索 / 执行 / 停止 / 请求人工决策
  ↓
执行受控动作
  ↓
核对实际结果与预期
  └──────────────→ 回到“更新决策记录与目标”

这个循环把“会不会推理”转换成了几个可以验收的问题：

环节应留下的证据失败时的处理
观察输入、时间、环境状态和信息缺口标记未知，不用猜测填空
规划候选路径、假设、收益、成本和风险缩小范围或请求更多信息
选择选择理由、预算和停止条件暂停，不自动扩大权限
执行工具调用、参数和返回结果记录失败，限制重试次数
验证预期与实际的对照回滚、修正或升级给人

表格是本文基于原帖做的工程化整理，不是原帖声称已经存在的标准协议。它的价值在于把“自主决策”拆成可以观察和复盘的状态，而不是把 Agent 的自主性理解成无限行动权限。

评价 Agent 时，别只看任务完成率

如果只统计“最后有没有完成”，会漏掉大量无效行动。更合适的观察指标包括：

  • 无效行动比例：没有改变目标状态、却消耗了工具调用或人工时间的动作占比。
  • 决策修正延迟：新证据出现后，系统多久能更新原判断。
  • 停止准确率：已经应该停止的路径是否及时停止，仍值得探索的路径是否被过早终止。
  • 人工介入成本：每次请求是否包含足够上下文，能否让人快速做出选择。
  • 验证覆盖率：关键动作中，有多少真正对照了预期和实际结果。

这些指标不能直接证明 Agent “更聪明”，但能帮助区分两种情况：它是在有效推进目标，还是只是在产生更多步骤和文本。

RSI 需要先说清楚边界

原帖最后提到“为系统构建 RSI 的能力”，并把它视为接下来有挑战的方向。本文将 RSI 保留为作者的表述，不把它直接等同于已经实现的 recursive self-improvement，也不据此推断某个系统能够自主改进模型本身。

在这条动态的语境里，更稳妥的理解是：系统能够利用执行结果、反馈和修正后的决策依据，持续改进后续行动。要把这件事写成可验证的工程能力，还需要明确版本、评测集、改动范围、回滚方式和人工批准点。

给 Agent 设计者的检查清单

在给 Agent 增加主动服务能力前，可以先问五个问题：

  1. 它是否保存了决策依据，而不只是最终答案？
  2. 它能否比较多条路径，并展示各自的风险和成本？
  3. 目标变化时，它能否修改或终止旧计划？
  4. 每个关键动作是否有独立的预期与结果检查？
  5. 需要人工介入时，问题是否足够小、足够明确，并且默认保持在可控范围内？

如果这些问题还答不上来，继续增加工具和并发数通常只会扩大失败半径。先把决策状态、停止条件和验证证据做完整，再讨论让 Agent 承担更多主动任务。
